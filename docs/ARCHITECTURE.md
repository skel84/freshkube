# Architecture

What the code is today, on main `6b5fdc9` (after #589, #591 and #593). It describes; [AGENTS.md](../AGENTS.md) holds the rules and the other docs hold each feature's behaviour. Every claim names the module that makes it true, so a stale line is one you can check. Paths are from the repository root.

## Crates and their direction

A crate may depend only on the crates below it. Read the arrows off each `crates/*/Cargo.toml`, not off this page.

```
src/main.rs (freshkube)      → freshkube-desktop, freshkube-probe
freshkube-desktop            → applications, core, delivery, logs, monitoring, nav, observability, prefs, probe, reads, resources, terminal, ui, talos-rs
freshkube-applications       → core, delivery, monitoring, nav, observability, probe, reads, resources, ui
freshkube-resources          → core, delivery, monitoring, nav, probe, reads, terminal, ui
freshkube-observability      → core, delivery, graph, logs, monitoring, prefs, ui
freshkube-delivery           → core, talos-rs
freshkube-monitoring         → core, prefs, probe, reads, ui, talos-rs
freshkube-logs               → core, probe, ui
freshkube-terminal           → probe, ui
freshkube-workbench          → graph, probe, ui          (never shipped)
freshkube-reads              → core
freshkube-nav                → core
freshkube-ui                 → graph, prefs, probe
freshkube-core               → talos-rs
freshkube-graph, freshkube-prefs, freshkube-probe, talos-rs                (no workspace dependencies)
```

The rules the graph shows:

- **`freshkube-core` has no GPUI.** Its manifest has no `gpui` dependency; cluster logic, domain types and the snapshot (`crates/freshkube-core/src/snapshot.rs`) are plain Rust. A screen calls core with real Rust types; there is no serialization boundary. The access a page is handed is core's too (`cluster_source`, below), though desktop still builds it.
- **`freshkube-ui` has no core.** The look (theme, tables, page frame, drawer, inspector) knows nothing of clusters. It depends on `freshkube-graph` (curve layout), `freshkube-prefs` (the text size file) and `freshkube-probe` only.
- **Feature crates sit under desktop and never name it.** Monitoring, Observability, Resources and Applications reach desktop only through their events (below). Observability and Resources use Monitoring; Monitoring uses neither. Applications uses Resources (`ResourceLink`, `ClusterSource`, the example objects) and Observability (`RevisionLink`); neither uses it.
- **`freshkube-reads` holds the shared, generic read owners.** `Loader<T, I>` (`crates/freshkube-reads/src/loader/mod.rs`) and `Watch<T, I>` (`crates/freshkube-reads/src/watch/mod.rs`) need core's `Snapshot`, `OwnedJob` and `spawn_job`, a GPUI `Task` and Tokio, so the crate depends on core, `gpui-kit` and Tokio, and on nothing of `freshkube-ui` or desktop. Monitoring uses completion loaders (`crates/freshkube-monitoring/src/page/`, `crates/freshkube-monitoring/src/history/`): its panels and page states keep the data, and one private `dispatch` in its `lib.rs` runs example or live work for both. Observability (`crates/freshkube-observability/src/connection.rs`) and `LogView` retain their feature-specific owners.
- **`freshkube-nav` holds where a link goes, and nothing that acts on it.** `ResourceLink` with the requests it carries (`LogsRequest`, `LogsAt`, `ShellRequest`), the objects it names (`ResourceIdentity`, `ObjectRef`, `DetailTarget`) and the tabs it opens on (the Resources pane's `Tab`, `NodeTab`) live in `crates/freshkube-nav/src/` (`request.rs`, `object.rs`, `tab.rs`), so a page crate can ask for navigation without naming desktop (#583). It depends on core alone, for `ResourceKind` and `PodContainers`, and has no GPUI. Desktop keeps their old paths with a re-export where each was defined: `crate::resources::{ResourceLink, LogsRequest, LogsAt, ShellRequest, Tab}`, `crate::resources::model::{ResourceIdentity, ObjectRef}`, `crate::resources::detail::DetailTarget` and `crate::desktop::nodes::NodeTab`. What desktop does with them stays in desktop, as extension traits beside the behaviour: the pane's strip of two tabs (`Strip` and `STRIP`, `resources/pane/mod.rs`) and a node tab's element id and retained screen (`NodeTabs`, `desktop/nodes/mod.rs`). `Page` and `Area` stay in `desktop/pages.rs`, since only the shell names them (Applications' UI tests name `Page`, through `Pilot`); `PageEvent` stays in `screens/page.rs`, since it wraps GPUI's `FocusHandle` and Monitoring's and Observability's events; and `NodeRow` stays in `desktop/nodes/join.rs`, a drawn row the Nodes join derives, not an identity. Resources reads none of it: when its rows change, the Nodes workspace builds each Kubernetes node's `NodeFacts` (`resources/node_facts.rs`, what the pods list's not-ready group and a pod's Runs on card show) with `NodeRow::resource_facts`, and the shell hands them over with `push_node_facts`.
- **Test-only edges are features or dev-dependencies.** The `testing` features and `freshkube-probe`'s `counting` are turned on only from `[dev-dependencies]` (desktop's, and for the feature crates their own), never from a normal dependency. Desktop also has a plain dev-dependency on `freshkube-graph`, for the map's tests.

Desktop reaches the moved code by its old paths in `crates/freshkube-desktop/src/lib.rs`: `crate::monitoring`, `crate::observability`, `crate::resources` and `crate::applications` are `use … as …` lines (the terminal's callers name `freshkube_terminal`), and `crate::palette`, `theme`, `text_size` and `stream_status` come from one `use freshkube_ui::{…}`. `crate::ui` is a module (`crates/freshkube-desktop/src/ui.rs`) that re-exports `freshkube_ui::ui::*` and adds desktop's own helpers, such as `health_tone`, the one map from a core `HealthIndicator` to a tag's tone and icon (`freshkube-ui` cannot name core's type). The delivery chain (Kargo, Argo CD, builds and pods) and the applications derived from it live in `crates/freshkube-delivery/` (`src/applications/`, `change/`, `changes/`, `entry/`), not in core. It sits between core and desktop/observability, depends on core and `talos-rs` only, and has no UI types. Its reads fail with core's `Failure`, whose kind is set where the read fails, and the words for refused, not served, unreachable and unfinished, singular and plural, come from `freshkube_delivery::words`, and a kind's own label (the first word of `Failure`'s display) from `FailureKind::label`. In core, delivery and Resources, a match on `FailureKind` that decides what a page shows (refused, not served, failed) names every kind and has no wildcard arm, so a new kind won't compile until it is placed; no screen decides from an error's words. The exceptions still to move are the shell's `failure_label`, Nodes' metrics-server sentences and `ObservationFailure::message`, besides what Applications composes itself. Core's other cluster reads outside delivery are partly converted: the Diagnostics pod and CNI reads, Maintenance's readiness reads and client setup, Operations' preview reads (`preflight_nodes`, `preflight_kubernetes`, `blocking_pdbs`), the monitoring marker reads (`monitoring/markers.rs`), and the Talos and talosconfig reads behind Security and Lifecycle carry `freshkube_core::failure::Failure`. They are built with `Failure::from_kube_text`, `from_talos_text` or `from_talos_formatted`, or with `Failure::new(from_kube(error).kind, …)` where the sentence is composed, or with a fixed kind where the failure isn't the error's (a deadline, a verdict, a setup step: Maintenance's setup classifies each step where its error is known), so the words on screen stay each call's own text (`from_kube` and `from_talos` word a failure for a banner instead); each page takes `failure.message`. The access chain (`cluster_source`'s client methods and the selection runner's `connect`) now carries `Failure` too: deadlines are `Timeout`, changed configuration is `Config`, and stopped inspection workers are `Other`. Talos's upstream `K8sError` has already erased setup causes into text, so those opaque failures remain `Other` with their complete display message until the upstream producers are typed (#584). Direct access keeps the existing connection failure's kind and its formerly displayed text as the message, including its kind label. Desktop's existing text and presentation wrappers take `.message` and keep their previous state, label and sentence; Monitoring's `cluster_client` similarly keeps `QueryError::Unavailable`, and Operations maps the typed connection failure to `.message` before its unchanged notes and audit. Still `String` are the parse and validation messages, the keychain's, and the selection runner's precheck (`run_with_preflight`'s `CheckFuture` and `SelectionOutcome.note` take `.message` and stay with the mutation path). Delivery's `testing` feature (`freshkube_delivery::testing`, `crates/freshkube-delivery/src/lib.rs`) holds what desktop's tests read and is turned on from desktop's `[dev-dependencies]`.

**Old paths and what each crate uses**, moved from [AGENTS.md](../AGENTS.md), which keeps the rules (#587). Shared components live in `freshkube-ui`, which depends on neither core nor desktop; desktop reaches its modules by their old paths (`crate::ui`, `crate::palette`, `crate::theme`, `crate::text_size`). Monitoring is `freshkube-monitoring`, which desktop reaches as `crate::monitoring`; it sits under desktop and uses only core, `talos-rs`, `freshkube-ui`, `freshkube-probe`, `freshkube-reads` and `freshkube-prefs` (its `monitoring.json`), so Resources and Observability depend on it, never the other way. Observability is `freshkube-observability`, which desktop reaches as `crate::observability`; it uses core, `freshkube-delivery` (for `change::example::POD_HASH`), `freshkube-ui`, `freshkube-logs`, `freshkube-graph`, `freshkube-monitoring` and `freshkube-prefs` (its `coroot.json`), and names nothing of desktop: the shell turns its `ObservabilityEvent`s into navigation, and desktop's tests reach its fixture links through its `testing` feature. Resources is `freshkube-resources` (desktop's old `resources/`, the port forwards in its `forwards/`), which desktop reaches as `crate::resources` and its forwards as `crate::forwards`; it uses core, `freshkube-delivery` (the example Applications' objects), `freshkube-monitoring` (a pod's history), `freshkube-nav`, `freshkube-probe`, `freshkube-reads`, `freshkube-terminal` and `freshkube-ui`, and names nothing of desktop: the shell hands it the cluster source and the node facts and hears its events. What desktop names of it is `pub` and the rest crate-private; desktop's tests read the screen through its `testing` feature (`detail_tab`, `selected_row`, `shell::ClosingTransport`, …). Its root keeps desktop's old paths to the crates it uses (`crate::ui`, `palette`, `meters`, `stream_status`, `perf`, `backend`, `fixture`). Applications is `freshkube-applications` (desktop's old `applications/`), which desktop reaches as `crate::applications`; it uses core, `freshkube-delivery`, `freshkube-monitoring`, `freshkube-nav`, `freshkube-observability`, `freshkube-probe`, `freshkube-reads`, `freshkube-resources` and `freshkube-ui`, and names nothing of desktop: the shell hands it the cluster source, the workspace's clusters and the visibility, and hears its `ResourceLink`, `SwitchLink` and `RevisionLink` events. The shell also hands it Observability's connection as an `OutcomeReader` and each workspace entry's Coroot link (`CorootLive`, from `Links::of` over the entries and the connection's project), so the change page reads what Coroot found after a deploy over the one connection the setup file names (`desktop/switch.rs`, `startup/setup.rs`). What desktop names of it is `pub` and the rest crate-private. Four test files that drive the whole shell (`Pilot`) stay in desktop, as `crates/freshkube-desktop/src/desktop/applications_tests/`, and read the pages through the crate's `testing` feature; the crate keeps its inline tests. `mono`, the mono-face text helper, moved to `freshkube-ui` beside `field`. Reads are `freshkube-reads`, whose `Loader` the screens own, with `Watch` for a stream and `OnShow` for what showing a hidden page does; it uses only core, GPUI Kit and Tokio, and names nothing of `freshkube-ui` or desktop. Delivery is `freshkube-delivery` (core's old `delivery/` and `applications/`, moved together because they refer to each other): desktop and observability reach it as `freshkube_delivery::{change, changes, entry, join, kargo, read, source, argocd}` and `freshkube_delivery::applications`, the old `freshkube_core::delivery::…` and `freshkube_core::applications::…` tails kept after the crate name. It uses core, `talos-rs` and no UI types; core names nothing of it (`workspace::Sources` and Argo CD's in-cluster name and server stay in core's `workspace`). Its other modules are crate-private, and so is every item no other crate names; a path a screen needs is made `pub` there. Desktop's tests read its example data and parsers through the `testing` feature (`freshkube_delivery::testing`), turned on only from dev-dependencies. Navigation's identities and requests are `freshkube-nav` (`ResourceLink`, `LogsRequest`, `LogsAt`, `ShellRequest`, `ResourceIdentity`, `ObjectRef`, `DetailTarget`, the Resources pane's `Tab` and `NodeTab`); it uses core alone and names nothing of GPUI or desktop, and desktop reaches them by their old paths (`crate::resources::{ResourceLink, LogsRequest, LogsAt, ShellRequest, Tab}`, `crate::resources::model::{ResourceIdentity, ObjectRef}`, `crate::resources::detail::DetailTarget`, `crate::desktop::nodes::NodeTab`). `Page`, `Area`, `PageEvent` and `NodeRow` stay in desktop.

**Preferences files.** `freshkube-prefs` (`crates/freshkube-prefs/src/lib.rs`; serde and serde_json only, no workspace dependencies, no logging) is where every preferences file is moving; `navigation.json`, `preferences.json`, `connection.json`, `monitoring.json` and `coroot.json` are on it. It holds a `Dir` resolved from the preferences path (`GpuiOptions.preferences`) and a `Document<T>` per file whose `load` gives the default for a missing file and, for an unreadable or unparsable one, the default and a problem for the caller to log once; its `save` writes a temporary file beside the file and renames it into place. A new file is created with the document's mode less the umask (Unix; Windows has no mode and takes its directory's), an existing one keeps its permissions. `Document::update` loads, lets a writer change its own keys and saves, one update at a time in the process, so a `Document<Map<String, Value>>` keeps every key its writer does not own, unknown ones included. `navigation.json` uses `load` and `save` (`crates/freshkube-desktop/src/navigation_file.rs`); `update` has one caller, the text size below. `Document::update` returns a read error other than "not found" and saves nothing, so a file it could not read is never overwritten; a file that parses wrongly starts from the default. `Document::limited_to` bounds a read, and `update` also refuses a file that limit rejects (too large, not a regular file) with an error. Each of the other three is a typed `Document` owned by its feature: `connection.json` (the remembered Talos or Kubernetes-only choice, `crates/freshkube-desktop/src/connection_preferences.rs`), `monitoring.json` (the dashboards folder and per-context sources, `crates/freshkube-monitoring/src/store.rs`) and `coroot.json` (the Coroot server, sign-in, project and reconnect flags; never the key, which stays in the credential store, `crates/freshkube-observability/src/remember.rs`). They write the whole file, so keys they do not know are not kept, and each logs a file it could not use. `preferences.json` holds only the text size, which `freshkube-ui`'s `text_size.rs` reads at start and writes on each change (pretty-printed, with a trailing newline, as before); it logs a bad file at start and a failed save once. `workspace.json` still has its own reader and writer. [#706](https://github.com/skel84/freshkube/issues/706) replaces it and `coroot.json` with one YAML setup file, `freshkube.yaml`; its design is [SETUP_FILE.md](SETUP_FILE.md). Its types, two-pass `parse`, `to_text` and `commit` are core's `setup` module (`crates/freshkube-core/src/setup/`); nothing reads or writes the file yet.

## What a page is

There are three ways to draw a page on main, and one trait every page has a handle through. #579 is moving pages onto that trait; its first three steps are on main. #591 added `PageEvent`, `PageSource` and `PageEventFn` (`crates/freshkube-desktop/src/screens/page.rs`) and the matching `ScreenPanel`/`ScreenHandle` methods. #599 made the shell tell every page with a handle whether it shows (`set_visible`) and hear the entity pages through `ScreenHandle::subscribe`. Step 3 keeps every page's handle in one map, `Pilot.pages.map`, a `BTreeMap<PageId, ScreenHandle>` (`crates/freshkube-desktop/src/desktop/page_map.rs`): the shell hands each page its source (`set_page_source`), tells it whether it shows, refreshes it, reads its status line and hears its events through that handle, in `PageId`'s order. `PageId`, which keys every page and lists the Talos screens in `PageId::SCREENS`, and the `Page`→`PageId` maps (`Page::id`, and `Page::screen` for the pages a screen draws) are in `crates/freshkube-desktop/src/desktop/pages.rs`. What still differs is how each kind of page draws and what it does with its hooks (below).

**1. A `ScreenPanel`** (`crates/freshkube-desktop/src/screens/mod.rs`). The trait has `set_source`, `activate`, `refresh`, `manual_refresh`, `focus`, `status`, `loading_motion`, `set_embedded`, `set_page_source`, `set_visible` (a no-op by default) and `subscribe_page`. A page makes itself with its own `new`, which the screen factory names; #599 took `new` out of the trait so that entities built another way can implement it. Nine Talos screens implement it: `EtcdScreen`, `WorkloadsScreen` (Health), `SecurityScreen`, `LifecycleScreen`, `OperationsScreen`, `ProcessesScreen`, `StorageScreen`, `NetworkScreen`, `DiagnosticsScreen`, each under `screens/<name>/`. They keep the default `set_visible`, which does nothing; `Loader` has its hook (`Loader::set_visible`), which #582 has them call. They are retained in `Pilot.pages.map` under their `PageId`s. `ScreenHandle` is the type-erased wrapper that lets the shell call every page from one map. A screen's `set_page_source` is its `set_source` with the source's `ScreenSource`, by default; the shell sends it to every screen and `activate`/`refresh` only to the visible one (`Pilot::push_source`, `Pilot::active_screen`).

**2. An entity the shell owns directly.** Resources, Monitoring, Observability, Applications, Settings, System services and Overview implement `ScreenPanel` (`crates/freshkube-desktop/src/desktop/entity_pages.rs`). Resources, Monitoring, Observability, Applications and Settings take their part of the `PageSource` in `set_page_source`, which hands it to the entity's own `set_source` (the `ClusterSource` for Resources, Monitoring and Observability, Applications' entry too), and their `set_visible` calls the entity's own. `refresh` calls the entity's own on Resources, Monitoring, Observability and Applications; Settings' does nothing. `status` gives the line of Resources, Observability, Applications, Settings and System services; Monitoring has none. System services and Overview take no source and keep the default `set_visible`: the shell feeds System services its nodes and the Talos reading, and Overview its cards, its attention rows and its state. `subscribe_page` hears each one's events. Their `set_source` and `activate` do nothing.

| --- | --- | --- |
| Resources | `ResourcesScreen` | `crates/freshkube-resources/src/screen/` |
| Monitoring | `MonitoringPage` | `crates/freshkube-monitoring/src/page/` |
| Observability | `ObservabilityPage` | `crates/freshkube-observability/src/lib.rs` |
| Applications | `ApplicationsPage` | `crates/freshkube-applications/src/` |
| Settings | `SettingsPage`, one page of sections (`settings/sections.rs`); only its Delivery sources list has `set_source` and `set_visible`, and it drops its check on hide or when another section shows | `crates/freshkube-desktop/src/desktop/settings/` (`sources/mod.rs`) |
| System services | `SystemServices`; its hooks do nothing but give its status line and hear `ServiceEvent`: the shell pushes the node roster's services with `set_nodes` (`desktop/target.rs`, `desktop/mod.rs`) and the read state with `set_reading`; the page makes no requests | `crates/freshkube-desktop/src/desktop/system_services/` |
| Overview | `OverviewPage`; its hooks do nothing but hear `OverviewEvent` (a card, an attention row's Open, Logs or Open node, a state's button), which the shell runs: `rebuild_joined_nodes` pushes the cards and attention rows with `set_display` and `set_attention`, and the shell's observer pushes `OverviewState` (where the Talos overview, the summary and the connection stand) after every notify, which redraws the page only when it changed. Show all is the page's own. The states and the stale banner are shared with the node pane's System services tab (`desktop/states.rs`) | `crates/freshkube-desktop/src/desktop/overview/` |

Resources, Monitoring, Observability and Applications cancel their reads on hide, Nodes stops its read of its nodes' use, which starts again on show (`desktop/nodes/metrics.rs`), and Settings drops its Delivery sources check, each from its `set_visible`. `Pilot::sync_visible` (`desktop/pages.rs`) tells the pages that show `true` and every other `false`, every page in the map in key order, whenever the page or the node pane's tab changes (`Pilot::navigate`, `sync_node_visibility` in `desktop/nodes/mod.rs`). A roster change that closes the pane or drops its tab has no window at hand, so `rebuild_joined_nodes` asks for it once its update ends (`Pilot::sync_visible_soon`). Visibility nests: a node pane's screen shows only while Nodes is up with its tab selected (`Pilot::shown_page`), and Nodes keeps showing around it, so both hear `true` (`Pilot::shown_pages`). Nothing else shows at once. Custom Resources (`resources/custom.rs`), the dock (`desktop/dock/`) and Command-K search (`desktop/search/`) are entities too, but are not pages: they sit beside whatever page shows.

**3. An entity the shell drives.** Nodes is `Entity<Nodes>` (`desktop/nodes/`), a view that draws itself (`Render for Nodes` in `desktop/nodes/view.rs`) and is the page's handle. Its hooks read its nodes' use and give what the status bar and the motion beside the page show: `set_page_source` keeps the Kubernetes connection and `set_visible` starts or stops the read (`desktop/nodes/metrics.rs`), which follows the page, since Nodes shows around a pane screen too; `status` gives the line the shell derives from the Talos overview and the summary session (`Pilot::rebuild_nodes_meta`), and `loading_motion` the table's motion while it draws loading rows, or else the open pane screen's. Otherwise the shell owns the node's selection across pages, the Talos reads and navigation, and writes what Nodes draws through `update`, so a notify of the shell alone does not redraw it; a notify of Nodes redraws the shell too, as an ancestor. Every click or key in Nodes emits a `NodesEvent` (`desktop/nodes/mod.rs`: open a node, step, close, back, step or show a tab, refresh, an attention row's destination), which the shell hears through `cx.subscribe_in` in `Pages::subscribe` once the listener's update ends, and runs in `Pilot::nodes_event`. Nodes observes the log view and the history chart itself, since neither is drawn while another tab shows, and draws again when collection starts or stops or the chart comes or goes. The node pane's System services tab is `NodeServices` (`desktop/services/`), a view of its own that Nodes draws: it owns the tab's filters, selection, focus and scroll, the shell hands it the services read (`set_reading`) and where the Talos overview and the node stand (`set_state`, redrawn only for a change), and it asks the shell through `NodeServicesEvent` for Logs, Restart, Refresh, the node's Pods and Overview. The read and the restart's ticket stay on the shell. The Nodes workspace (`crates/freshkube-desktop/src/desktop/nodes/`) also **embeds** four `ScreenPanel`s in its node pane (`NodeTabs::screen`: Processes, Storage, Network, Diagnostics) and the Resources and log views, laid out by the pane's width (`screens::set_node_pane_width`), not the window's. Nodes holds the shell's Talos log view and clones of the four screens' handles, taken from `Pilot.pages.map` once it is built, only to draw them; the map stays where the screens hear the shell, and the shell still drives the log view.

**Navigation.** `shell::Navigation` (`desktop/shell/navigation.rs`) is a plain struct, not an entity, that `Pilot` owns once as `navigation`: the page shown, the rail's area, the kind remembered per group, and the column's state, lines, reveal and scroll handles, and the rail's marks. Its methods are those that touch only those fields (and, for the column's fold and width, the window's size): the column's width and fold, the sidebar row a page sits on, the kind memory, the title; what also needs a page, the session or the `Context` (`navigate`, `open_kind`, `show_area`, `toggle_column`) stays on `Pilot` and reaches through `self.navigation`. The Command-1…9 keys name a `Page` (`Pilot::show_page`) or, for Namespaces and Events, a built-in kind.

**Chrome.** `shell::Chrome` (`desktop/shell/chrome.rs`) is a plain struct, not an entity, that `Pilot` owns once as `chrome`: the cached header, rail and column (`ChromeParts`, each a `CachedPart` view), the countdown ring with whether Talos refreshes by itself and the time since the last refresh, the status bar's fps readout and forwards indicator, the appearance, and the app menu's state (the menu platform, the menu button's open menu and the focus it acts on, and what the installed menus state). `Chrome::new` makes its views with the shell and subscribes to what is its own: the window's appearance, which it follows while the appearance is the system's. `Chrome::set_appearance` follows the theme chosen. What also needs a page, the session, `Navigation` or the shell's `Context` stays on `Pilot` and reaches through `self.chrome`: the countdown's tick (`tick_countdown`, which reads whether anything loads), setting the menus again (`sync_menus`), opening the app menu, and each part's `render_*`. What redraws a cached part is unchanged: each part observes the shell, and the column also the pages it reads (`ChromeParts::watch`, called once the shell exists).

**Construction.** `Pilot::new` (`desktop/mod.rs`) composes the shell from its owners, in an order that matters, since GPUI calls an emitter's observers in the order they were made:

1. It installs the navigation file and the shell's keys, and makes the session's talosconfig input (`talosconfig_input`).
2. `subscribe_shell` observes the shell itself, which pushes its state into Overview and Nodes, and the operations slot, before the Operations screen does; it also sets the window's close guard.
3. `page_map::Pages::new` (`desktop/page_map.rs`) makes every page in a fixed order and returns the page set (`Pilot.pages`: the map, `Pages.map`, and the typed handles the shell keeps beside it). The session's age label is made by the caller and handed in, since Overview draws it.
4. `observe_theme` runs after the pages, so Observability hears a theme change first. Then `Pages::subscribe` hears Logs, every page in the map and what the map doesn't hold.
5. It starts the one-second tick, then makes `Chrome`, the Command-K palette and `Navigation`.
6. `with_session` makes the struct: the session's fields as they start, which #44 will move into a session owner, around the owners handed in as one `Owners`.
7. `start` reads the workspace and opens the first source, then wires what needs the shell itself: the switcher's and the menus' observers and `ChromeParts::watch`. It takes focus, opens a debug start-up page and pushes Overview's first state.

**Drawing.** `Render for Pilot` (`desktop/view.rs`) places what each owner draws. It tells the fps readout that the frame started (`Chrome::frame_started`), has `Navigation::lay_out` set the chrome's width and give the column's, and draws the shown page (`Pilot::render_page`: cached, except Monitoring, whose comment says why). Around the page cell it lays the cached header, rail and column (`ChromeParts::header`, `rail` and `column`), then the status bar and, beside the page, its loading motion and flash. The key context, `SHELL_CONTEXT`, stays on the root, which is drawn in every state. Each owner adds its actions to that root, and their handlers still run on `Pilot`: `Navigation::listen` the pages' numbers, Ctrl-Tab and Command-B, whose keys `Navigation::bind_keys` binds; `Chrome::listen` Settings, About, the appearance and the menu button, whose keys `freshkube_ui::platform::bind_keys` binds; and `Pilot::listen` what needs the session or the pages: Refresh, the previous and next context, Go to kind and the dock's tabs. `bind_shell_keys` binds Refresh, then Navigation's keys, then the rest, so the keymap's order is unchanged; `the_shell_binds_the_keys_and_actions_it_did` (`desktop/tests/keys.rs`) pins the bindings and the actions the root answers.

Cached views, render probes and the reasons for them are in AGENTS.md ("Keep render cheap").

## The session and the source

The shell holds one cluster at a time. The pieces, from the user's choice down to what a page reads:

- **`Registry`** (`crates/freshkube-desktop/src/desktop/session.rs`) owns the active `ClusterSession` and the parked ones. A session keeps the Kubernetes summary, its reflector job and task, and the access it was collected under. Switching workspace entries parks the active session and keeps nothing running. `docs/ACCESS_IDENTITY.md` has the contract.
- **`AppliedConfig`** and **`Target`** (`crates/freshkube-desktop/src/backend.rs`): the applied talosconfig path and context, and a node request identity (epoch, context, node, address). Node selection advances the epoch; access replacement invalidates targets.
- **`ScreenSource`** (`screens/mod.rs`) is what a `ScreenPanel` is given: the `Target`, the node roster (`NodeSummary`) and, unless this is example data, a `LiveSource` (Talos client, cluster overview, collector, talosconfig path and the applied access; `crates/freshkube-core/src/cluster_source/talos.rs`).
- **`ClusterSource`** (`crates/freshkube-core/src/cluster_source/mod.rs`) is what the Kubernetes-facing entities, Monitoring and Observability are given: an `id` that covers the access but not the target node, the context's name, and a `ClusterAccess`: `Example(Hold)` (made-up data, with what it never answers; `ClusterAccess::EXAMPLE` holds nothing), `Talos(Box<TalosAccess>)` (the client the Talos side sets up), `Direct(DirectAccess)` (a kubeconfig context, for `--kubernetes-only`) or `Live(Arc<dyn KubeClientSource>)`, which the app never builds and Monitoring's tests use for fakes that count what they are asked. `TalosAccess` and `AppliedAccess` are in `talos.rs`, `DirectAccess` in `direct.rs`; desktop re-exports them at `resources::screen`, `resources::talos`, `resources::direct` and `screens`.
- **`AccessIdentity`** (`crates/freshkube-core/src/client_cache.rs`, used by `session.rs`) names an access session plus the inspected configuration revision. With Talos access `ClusterSource.id` is its key; kubernetes-only uses `DirectAccess::id()` and the fixture `resources::example::connection(context)`.

`Pilot::source` (`crates/freshkube-desktop/src/desktop/source.rs`) builds the one `PageSource` every page is handed: the `ScreenSource`, the `ClusterSource`, the workspace entry and the access identity, which stays set while the source is missing for a while. One match there decides between example data, a kubeconfig context and Talos, and the Talos arm builds the `LiveSource` once for both the screens and the `ClusterSource`. It is the session owner until #44's session type takes it. The kubeconfig-only mode (`desktop/kubernetes_only.rs`) and the fixture mode (`--fixture`, below) are not separate shells: they change what `Pilot::source` returns. What the window shows is `Pilot.mode`, a `Mode` in the same module: two answers, `Mode::is_example` (with `Mode::example` for its hold) and `Mode::has_talos` (with `Mode::kubernetes_only` for the kubeconfig and its connection), and example data's clock. They are independent: example data is Kubernetes-only too after "Use Kubernetes only…" under `--fixture`. Readers ask `Pilot::mode()`; the Kubernetes-only flow changes it through `Mode::set_kubernetes_only`, `Mode::kubernetes_only_mut` and `Mode::leave_kubernetes_only`, and the example refresh takes `Mode::next_tick`. The example answer, with its hold, is set once, from the launch options.

`Pilot::push_source` is the single fan-out. It hands that `PageSource` to every page in the map in two passes, the Talos screens first and the other pages last, in key order; between them search, Custom Resources and the dock, which sit beside the pages, get the `ClusterSource` through plain shell calls in that order. Nodes hands its own Pods list the source in `Nodes::set_page_source`, before its use read. A page compares the new source with the old one and drops its data and jobs when the identity changed.

## Reads: `Snapshot`, `Loader` and the exceptions

- **`Snapshot<T, I>` and `Request<I>`** (`crates/freshkube-core/src/snapshot.rs`) keep the last good value for one identity and refuse an answer for a superseded request. Desktop names it `state::Snapshot<T, I = AppliedConfig>` (`crates/freshkube-desktop/src/state.rs`). The transitions are tabulated in `docs/STATE_LIFETIMES.md`.
- **`OwnedJob` and `spawn_job`** (`crates/freshkube-core/src/job.rs`; re-exported by `crates/freshkube-desktop/src/backend.rs`) run Tokio work under a deadline; dropping an `OwnedJob` aborts it. The GPUI delivery `Task` that applies the answer is kept beside it, and the answer is checked for identity and generation before publishing.
- **`Loader<T, I>`** (`crates/freshkube-reads/src/loader/mod.rs`) is a `Snapshot`, an `OwnedJob` and a `Task` together: `load`, `resolve` (fixtures), `reset`, `data`, `error`, `is_loading`, `is_stale`, `last_successful`. An owner whose answer needs more than `load` gives (work of its own, a window, or derived data as it lands) begins the read with `start`, hands its job and task to `run` and lands the answer with `land`, which times it as `load` does; a read given no work, as example data held on its loading rows, waits until replaced or hidden, and `expire` counts what was read as old. The nine Talos screens use desktop's wrapper `screens::Loader<T>` (`crates/freshkube-desktop/src/screens/loader.rs`), which fixes the identity to `Target` and the deadline to core's `constants::SCREEN_DEADLINE`. `set_visible(visible, OnShow, cx)` (`crates/freshkube-reads/src/visibility.rs`) drops the read on hide and keeps the data as last known; on show it returns whether to read again: `OnShow::ReadIfOlder(threshold)` past that age of the last successful answer, or `OnShow::Never`. The three Applications owners are its first callers, each with `OnShow::ReadIfOlder(FRESH_FOR)` (30 s) and `start`, `run` and `land`: the list (`ApplicationsPage`, a `Loader<Read, (String, Option<String>)>` for the connection and its workspace entry, `crates/freshkube-desktop/src/applications/mod.rs`), the Changes list (`ChangesPage`, keyed by the connection, `applications/changes/mod.rs`) and the change page (`ChangePage`, keyed by the change, `applications/change/read.rs`, whose answer lands in its window to select its Stage).
- **`Watch<T, I>`** (`crates/freshkube-reads/src/watch/mod.rs`) is the same for a stream: `start` runs Tokio work that sends into a channel, and a GPUI task hands the owner what arrived in batches paced by `Pace` (`capacity`, `most`, `every`), each checked for identity and generation; `stop`, `is_running`, `revision` and `set_visible`, which stops a running stream on hide and asks for a new start on show. Resources' list watch is its first owner (`ResourcesScreen::start_watch`, `crates/freshkube-resources/src/screen/mod.rs`): a `Watch<Vec<ResourceEvent>, u64>` for the store session's epoch, paced by `WATCH_PACE` (every batch that arrived, at most once per `WATCH_COALESCE`). The store keeps its epoch for the example data and the tests' deliveries, which apply without a stream. `open` starts the delivery with no Tokio work, so only senders taken with `sender` feed it (work beside the watch's own, or an example writer on the GPUI clock), and `start_then` runs an `ended` hook on the owner when the stream ends by itself after its last batch. The log streams are on it too (#582): a Talos collection is a `Watch<StreamEvent, Target>` started with `start_then`, so one that runs out lands what it held while hidden and stops collecting (`crates/freshkube-desktop/src/logs/talos/mod.rs`); a pod's chosen container is a `Watch<PodLogUpdate, (ResourceIdentity, String)>` (`logs/pod/mod.rs`); a workload's pod watch is a `Watch<WorkloadPods, (ResourceIdentity, String)>` with room for one listing, whose work reads the newest listing only once that room is free, so a burst lands the listing in flight and then the newest (`forward_listings`, `logs/workload/mod.rs`); and `StreamSet`'s shared feed, which every container stream of a workload or of a pod's All containers sends into, is one `open`ed `Watch<Fed, Option<ResourceIdentity>>`, so they still land in one delivery and one ingest a frame (`logs/streams.rs`). Each container stream there keeps its own `OwnedJob`, generation and jittered retry, since the feed's one channel is what caps them together. The example writers run on the GPUI clock, never Tokio's. `dock/feed.rs` still delivers by hand.
- **Features with their own owners** keep them: Monitoring and Observability hold read/delivery pairs and a generation of their own; `LogView<S>` (`crates/freshkube-logs/`) owns its source, whose streams are `Watch`es; Resources owns its namespace, usage and detail reads, and its list's `Watch`; Custom Resources owns its discovery reads. `docs/STATE_LIFETIMES.md` lists each owner.

**The two exceptions to "a page reads only while it is shown":**

1. **Work the user or the session started, which runs while hidden.** The cluster summary session (nine reflector stores, `ClusterSession.summary_*` in `session.rs`, `crates/freshkube-desktop/src/desktop/kubernetes_summary/`); each dock log tab (`crates/freshkube-desktop/src/desktop/dock/`, `feed.rs`); a pod shell (`crates/freshkube-resources/src/shell/`); a port forward (`crates/freshkube-resources/src/forwards/`, reached by its old path `crate::forwards`). A log tab ends when closed or on a context, kubeconfig or talosconfig change; a running shell does too, after the shell asks (`shell::unless_shell`); a forward ends only on Stop and runs on through page, context and kubeconfig changes (`resources/forwards/mod.rs`, `desktop/switch.rs`).
2. **Operations mutations.** A submitted run holds the app-wide operation ticket in a detached delivery task until core's runner ends (`crates/freshkube-core/src/operations/`, `crates/freshkube-desktop/src/mutation.rs`); it is never an ordinary `OwnedJob` and navigation does not cancel it.

Everything else is meant to read only while shown. The entity pages drop their reads from `set_visible`; the Talos screens do not yet drop an in-flight read on hide (#582): `Loader::set_visible` is the hook, and only the three Applications owners call it yet.

## How a page reaches the shell

A page never holds the shell. It emits a typed event, and the shell subscribes when it builds the page.

- **Screens** emit `ScreenEvent` (`RefreshSummary`, `Back`, `OpenLogs`, `SelectNode`, `RetryCluster`, `OpenLogsOn`; `screens/mod.rs`), which reaches `Pilot::page_event` as `PageEvent::Screen` and goes on to `Pilot::screen_event` (`desktop/mod.rs`).
- **Entity pages** emit their own types: `ResourceLink` (Resources, Applications), `RevisionLink` and `SwitchLink` (Applications), `NodePodsEvent` (the node's Pods list), `DockEvent` (the dock), `ObservabilityEvent`, `MonitoringEvent` and `NotServed` (Resources). System services emits `ServiceEvent` (`desktop/system_services/mod.rs`) and Overview `OverviewEvent` (`desktop/overview/mod.rs`), which reach `page_event` as `PageEvent::Service` and `PageEvent::Overview`. The shell hears every page from one place, `Pages::subscribe` (`desktop/page_map.rs`), which `Pilot::new` calls before any page emits, since GPUI activates a subscription only after the current update. It loops over the page map, hearing each page through its `ScreenHandle::subscribe` (`Pilot::hear_page`, `desktop/entity_pages.rs`) with a `WeakEntity<Pilot>` trampoline into `Pilot::page_event`, then hears what the map doesn't hold. The node's Pods list and the dock, which aren't pages, have their events wrapped in `PageEvent` for the same `page_event`. Two event types aren't `PageEvent`s yet and keep their own arms there: Nodes, the page's handle with hooks that do nothing, emits `NodesEvent` (`desktop/nodes/mod.rs`), run in `Pilot::nodes_event`, and the node pane's System services tab, which isn't a page, emits `NodeServicesEvent` (`desktop/services/mod.rs`), run in `Pilot::node_services_event`. Each subscription hears one emitter and one event type, so the order the shell hears events in follows the order they are emitted. A test that clicks or presses in Nodes parks (`cx.run_until_parked()`) before it looks.
- **Object links** all end in `Pilot::open_object` (`desktop/pages.rs`) through `Pilot::resource_link` (`crates/freshkube-desktop/src/desktop/object_links/`); a link to a cluster that is not open is refused with a notice, and one to another workspace entry goes through `Pilot::open_on_entry` (`desktop/switch.rs`); `open_object` can also divert a link from another entry's ended connection (`divert_link`, `switch.rs`).
- **Redraws** use `cx.observe`, among others on the dock and Custom Resources, which notify the shell.

There are about a dozen event types. `PageEvent` (`screens/page.rs`) wraps all of them, and `Pilot::page_event` handles every variant. Every page in `Pilot.pages.map` is heard through `ScreenHandle::subscribe`; the node's Pods list and the dock through `cx.subscribe_in`, in the same `Pages::subscribe`.

An owner subscribes to what is its own in its constructor: `Chrome::new` to the window's appearance, each `CachedPart` to the shell. What also needs the pages, the session or both owners stays on `Pilot`: its own observer, which hands Overview and Nodes where things stand; Operations' slot, which redraws the cached pages and the status bar; the theme, which places the window controls, sizes the context name and redraws the cached pages; Logs, whose start and stop the shell shows; Settings, which rebuilds the cluster switcher; the menus (`watch_menus`), which state the sidebar, the dock and the appearance; and the pages themselves. `Navigation` holds no subscription.

## Where example data lives

`--fixture` builds `GpuiOptions::fixture()` (`crates/freshkube-desktop/src/lib.rs`), whose `starts_with_examples()` makes `Pilot.mode` example data; no credentials or cluster are touched. Pages then resolve from example data instead of reading:

- Talos side: core's `example::cluster` (`crates/freshkube-core/src/example/cluster.rs`: the contexts, the cluster and its nodes, services and logs), which desktop reaches by its old path, `fixture` (`crates/freshkube-desktop/src/fixture.rs`), plus `screens/<name>/example.rs` for each screen but etcd, whose example is in `screens/etcd/mod.rs`; `crates/freshkube-desktop/examples/fixture.rs` runs it standalone. Node-inspection example builders live in `crates/freshkube-core/src/example/`; Processes, Diagnostics, Network, Security and Storage use `ExampleNode` with `example::processes`, `example::diagnostics`, `example::network`, `example::kubespan`, `example::security` and `example::storage`; desktop keeps the source checks and input adapters in their `screens/<name>/example.rs`. Network passes sample and handshake times into core and keeps its display wrappers in desktop. Security takes the context, target address, endpoints and certificate time as plain values. Storage returns Talos disks and a volumes result; desktop keeps `StorageData`.
- What example data holds back: `cluster_source::Hold` (`crates/freshkube-core/src/cluster_source/hold.rs`), carried on `ClusterAccess::Example` ([the debug knobs](#where-the-debug-knobs-are-parsed)).
- Resources: `crates/freshkube-resources/src/example/` (objects, the acme workspace's Kargo and Argo CD kinds); `resources/shell/example.rs` (a local shell); `resources/forwards/example.rs` (a loopback listener).
- Applications and changes: `crates/freshkube-applications/src/example.rs`; in delivery, `crates/freshkube-delivery/src/applications/example.rs`, `change/example.rs` and `changes/example.rs`. Its `fixtures.rs` is a fake cluster for tests only (`#[cfg(test)]`), not example data.
- Monitoring and Observability: `crates/freshkube-core/src/monitoring/example.rs`; `crates/freshkube-observability/src/example.rs`, `application/example.rs`, `logs/example.rs`.
- Maintenance mode: `crates/freshkube-desktop/src/maintenance/example.rs`.
- The shared components on invented data: `crates/freshkube-workbench/src/stories/`.

Example names are invented (acme, cluster-a/b/c, shop-api, `core-fra`-style entries); a test or capture must never need a real cluster.

## Where the debug knobs are parsed

Every desktop knob is parsed in `DebugOptions`, and the build that honours it is decided in `DebugOptions::from_env`. Only the binaries' mains read the environment, besides the probe's first-frame switch (the probe's own), the dev examples; `talos-rs` reads none, since `TalosConfig::default_path_in` takes the values and talosctl's discovery helper takes the config path.

- Page, kind, theme, sidebar, dashboard, log search, motion and window size, the etcd and Applications example shapes, the fixture holds, the app menu button and the text size: `DebugOptions` in `crates/freshkube-desktop/src/debug_options.rs` (`FRESHKUBE_PAGE`, `_KIND`, `_THEME`, `_SIDEBAR`, `_DASHBOARD`, `_LOG_SEARCH`, `_MOTION`, `_WINDOW_SIZE`, `_ETCD`, `_APPLICATIONS`, `_FIXTURE_HOLD`, `_APP_MENU`, `_TEXT_SIZE`). `DebugOptions::from_env` reads them once, in `src/main.rs`, the stress binary and `examples/fixture.rs`, under `any(debug_assertions, feature = "stress")`; any other build gets the default (`_ETCD`, `_APP_MENU` and `_TEXT_SIZE` were only ever honoured by debug builds, so `from_env` clears them outside `debug_assertions`). It travels through `GpuiOptions::with_debug`; `desktop/startup/mod.rs` and `desktop/mod.rs` read its fields and never the environment; the pages are handed their value by `page_map::Pages::new`. `DebugOptions::parse` takes a lookup function, so its tests set no variables.
- Debug builds only: acting on `FRESHKUBE_LOG_SEARCH` (`startup/mod.rs`) and `FRESHKUBE_PAGE=maintenance` (`desktop/mod.rs`, which hands the maintenance example the struct's theme).
- Fixture holds: core's `cluster_source::Hold::parse` (`crates/freshkube-core/src/cluster_source/hold.rs`, re-exported as desktop's `fixture::Hold`) turns `FRESHKUBE_FIXTURE_HOLD` into `DebugOptions::hold`. `Pilot::new` keeps it in `Pilot.mode` as example data's own, `Mode { example: Option<Hold> }`, so live data has no hold; that is the one place a hold is set. The shell holds the Talos overview and the Kubernetes summary through `Mode::holds_talos`, and `Pilot::source` (`desktop/source.rs`) puts the whole hold on the example source, `ClusterAccess::Example(hold)`: Resources and Nodes' Pods read `lists` from it, and Applications and the Changes list `applications`, when the source arrives. Observability reads `coroot` from it: example access fills its examples when it arrives, and a held one leaves its tables on their loading rows. Coroot's examples don't wait for Talos, so under the Talos hold the shell's held `Pilot::refresh` hands Observability alone the source. Monitoring reads `monitoring` from the source it keeps, so a held example source leaves every panel on its loading state; under the Talos hold it has no source and asks nothing. `page_map::Pages::new` hands no page a hold. Tests set `GpuiOptions::holding_talos` (which sets `DebugOptions::hold.talos`), `Pilot::set_hold` or `Mode::hold_mut`. The stress binary sets it for its child (`crates/freshkube-desktop/src/bin/stress/main.rs`).
- Example shapes: `FRESHKUBE_ETCD` is `DebugOptions::etcd`, handed to `EtcdScreen::with_example` (`screens/etcd/mod.rs`); `FRESHKUBE_APPLICATIONS` is `DebugOptions::applications` (`applications/example.rs`'s `Variant::parse`), handed to `ApplicationsPage::new`, which maps it to delivery's `Shape` (`crates/freshkube-delivery/src/change/example.rs`) for the Changes list; delivery reads no environment for it.
- The app menu button: `DebugOptions::app_menu_button` (`FRESHKUBE_APP_MENU`), read by `Pilot::new` through `app_menu::menu_platform` into `shell::Chrome::new` (`crates/freshkube-desktop/src/desktop/app_menu/mod.rs`). The text size: `DebugOptions::text_size` (`FRESHKUBE_TEXT_SIZE`), passed to `freshkube_ui::text_size::install_with` (`crates/freshkube-ui/src/text_size.rs`, which reads no environment; its `parse` keeps one of `STEPS`).
- First-frame timing: `first_frame::start()` in `crates/freshkube-probe/src/first_frame.rs`, called from `src/main.rs` (`FRESHKUBE_FIRST_FRAME`).
- The stress binary: `StressOptions` (`crates/freshkube-desktop/src/stress.rs`) holds `FRESHKUBE_STRESS_KEYS`, `_SECONDS`, `_WARMUP`, `_APPEARANCE`, `_TALOS_RATE` and `_WORKLOAD_RATE`. `bin/stress/main.rs` parses them once (`StressOptions::from_env`), installs them for the log floods and the key script (`install_stress_options`, set once, like `Ambient`), and hands `_SECONDS` to its summary. Bad and missing values take the defaults they always had. `scripts/stress.sh` only exports the variables.
- The ambient values core uses (`FRESHKUBE_KUBECONFIG`, `KUBECONFIG`, the home directory, `HTTPS_PROXY`/`NO_PROXY` and their lower-case forms, `USER`/`USERNAME`, `TALOSCONFIG`): `freshkube_core::ambient::Ambient` (`crates/freshkube-core/src/ambient.rs`). Core reads no environment variable. `freshkube_desktop::install_ambient_from_env` reads them once, in `src/main.rs`, the stress binary and the dev examples, and installs them for core; a pure function of an `Ambient` decides each case (`resources/contexts.rs`, `client_cache.rs`, `kube_client.rs`, `operations/mod.rs`), and the tests pass values. `Ambient` must mirror what kube itself reads in the same process: kube takes `HTTPS_PROXY` when it builds a `Config` and `KUBECONFIG` (then `~/.kube/config`) through `Kubeconfig::read`, and core knows a proxy came from the environment, and which files the Automatic selection watches, only by comparing with this value. So every process that calls core's kube functions (binaries, examples, test harnesses) installs it before its first client; a process that installs nothing sees an empty value, so kube still proxies but core's loopback and `NO_PROXY` exemption is off. `TALOSCONFIG` goes to `TalosConfig::default_path_in` (the pure form of `default_path`, in `talos-rs`) through `ambient::default_talosconfig_path` and `load_default_talosconfig`, which core and desktop call; a set but empty value still wins and yields an empty path, one that is not UTF-8 counts as unset, and `src/main.rs` keeps its own rule (`talosconfig_or_env`: non-empty, and not with `--fixture`, Kubernetes-only, `--kube-context` or `--insecure`). A second install with a different value panics. UI tests install a hermetic value (`desktop/testing.rs`): the real proxy pair, a temporary home, no kubeconfig variables, a fixed user.
- Outside the app: the workbench's `main.rs` reads `FRESHKUBE_STORY`, `_THEME`, `_WINDOW_SIZE` and `_TEXT_SIZE` in a debug build into `freshkube_workbench::Options` (`crates/freshkube-workbench/src/lib.rs`), which `run` takes; core's `examples/probe.rs` reads `FRESHKUBE_CONTEXT`, `_NAMESPACE` and `_VERSION`.

The command-line options are `src/main.rs`'s `Cli`, which builds a `GpuiOptions` (`crates/freshkube-desktop/src/lib.rs`).

## Log views

Every log view is `LogView<S: LogSource>` from `freshkube-logs` (`crates/freshkube-logs/src/`). It owns retention, search, selection, copy, the level filter, follow, wrap and row measurement; a source (`TalosLogs` in desktop's `logs/talos/`, `PodLogs` in `logs/pod/`) supplies its toolbar tools and the note under them (`tools`, `notes`), its empty message and per-stream errors, and feeds lines through `ingest`. A source reaches the view only through the crate's `source_api.rs`; the view's other fields stay private to it, so a source's own methods live in an extension trait (`TalosPanel`, `PodLogPanel`) that callers import, and its stream methods on a trait private to `logs/`. Desktop's tests read the view through the crate's `testing` feature, turned on only from dev-dependencies. A new kind of log adds a source; it never copies the view.
