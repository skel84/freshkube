# The frame, the Overview and the Kubernetes summary

The behaviour of the app frame, the Overview and the session that feeds them, moved from [AGENTS.md](../../AGENTS.md) unchanged apart from its link paths: the three paragraphs starting "The frame (`desktop/shell/`)…", "Overview derives its cards…" and "The Kubernetes summary session…", and the GPUI rule's detail starting "The shell's Kubernetes summary is session-owned…".

Code:

- `crates/freshkube-desktop/src/desktop/shell/` is the frame: `header.rs`, `rail.rs`, `column.rs`, `source.rs`, `chrome.rs`, `frame.rs`; the settings pages are `desktop/settings/`, their sections `settings/sections.rs`, the switch is `desktop/switch.rs`.
- `crates/freshkube-desktop/src/presentation/` derives the Overview's cards (`overview/`) and Attention (`attention/`).
- `crates/freshkube-core/src/kubernetes_summary/` is the session; `crates/freshkube-desktop/src/desktop/kubernetes_summary/` hands it to the shell.

Tests that prove it (the files with a `#[test]`, `#[tokio::test]` or `#[gpui_kit::test]`, found with `git grep -l '#\[test\]\|#\[tokio::test\]\|#\[gpui_kit::test\]'` run over `desktop/shell/`, `desktop/tests/`, `desktop/settings/`, `presentation/`, `desktop/kubernetes_summary/` and core's `kubernetes_summary/`):

- The frame, `crates/freshkube-desktop/src/desktop/`: `tests/{chrome,column,custom,header,keys,kubernetes_only,layout,motion,observability,operations,overview,rail,screens,services,settings,shells,status,target}.rs`; inline tests in `shell/{column_state,context,fps,rail}.rs`; `switch_tests.rs`, `link_tests.rs`, `object_links/tests.rs`, `search/tests.rs`, `startup/tests.rs`, `settings/tests.rs`, `settings/edit_tests.rs`, `settings/destinations/tests.rs`, `settings/sources/tests.rs`.
- The Overview, `crates/freshkube-desktop/src/presentation/`: `tests.rs`, `attention/tests.rs`.
- The summary session: `crates/freshkube-desktop/src/desktop/kubernetes_summary/tests.rs`; core's `crates/freshkube-core/src/kubernetes_summary/`: `session_tests.rs`, `driver_tests.rs`; inline tests in `driver.rs`, `mod.rs`, `observation.rs`, `project.rs`, `requests.rs`, `retained.rs`, `session.rs`, `summarize.rs`.

The frame (`desktop/shell/`) is a 44 dp header, a 64 dp icon rail, a 208 dp column for the rail's area and a 28 dp status bar ([docs/DESIGN.md](../DESIGN.md)). The dock, when it has tabs, sits in the page cell under the page, as a cached view with an explicit height; `freshkube_ui::page::set_below` tells pages the room it takes. The rail's areas (`Area` in `desktop/pages.rs`) are Overview, Nodes, Namespaces, Events, Applications, Monitoring and Observability; the six Kubernetes groups and Custom Resources; Control plane; and Settings, last. The groups, Custom Resources, Control plane, Monitoring, Observability, Applications and Settings have a column: a group's kinds (Health first under Workloads), the API groups, the Talos pages, the dashboards, the destinations, the applications, or Settings' sections. A group's rail button reopens its last kind. Its problem dots (`RailMarks`) are derived with the Overview's cards. `screens::page_width` subtracts the rail and, when shown, the column. Where the shell is (the page, the area, the kind memory, the column and rail scroll state) lives in `shell::Navigation` (`shell/navigation.rs`), which `Pilot` owns as `navigation`. What the frame shows beside the page (the cached header, rail and column, the countdown, the fps readout, the forwards indicator, the appearance and the app menu's state) lives in `shell::Chrome` (`shell/chrome.rs`), which `Pilot` owns as `chrome`; it follows the system's appearance itself, from `Chrome::new`. `Render for Pilot` (`desktop/view.rs`) draws the frame from them and the shown page, and each adds its own actions to the shell's root ([ARCHITECTURE.md](../ARCHITECTURE.md#what-a-page-is)). What the window knows of the workspace's entries (the session registry, how the active entry was defined, the entry and link waiting to open, the restored time and the age label, the header's list) lives in `switch::Switcher` (`desktop/switch.rs`), which `Pilot` owns as `switch`; its methods touch only that state, and the steps of a switch that also need the pages, the session or the window stay on `Pilot` and call it. The selected Talos target (the overview's nodes, the selected node, its services and their read, and the object-link lookup tied to the target's epoch) lives in `target::Selected` (`desktop/target.rs`), which `Pilot` owns as `target`; its methods touch only that state, and the steps that also need the overview, the pages or the window (`sync_nodes`, `select_node`, `refresh_services`) stay on `Pilot` and call it. `Pilot::new` composes the shell from these owners, the page set (`page_map::Pages::new`, `desktop/page_map.rs`, which `Pilot` owns as `pages`) and the session's fields (`Pilot::with_session`), then starts it (`Pilot::start`) ([ARCHITECTURE.md](../ARCHITECTURE.md#what-a-page-is)). The shell hears every page's events from one `Pages::subscribe` ([ARCHITECTURE.md](../ARCHITECTURE.md#how-a-page-reaches-the-shell)). Command-1 through Command-9 follow Overview, Nodes, Namespaces, Events, Health, etcd, System services, Security and Lifecycle; Control-Tab also visits the last other kind. Kubernetes-only mode starts on Overview, and its Control plane column offers a talosconfig instead. Node inspection and service logs live in the node pane; the header holds the context switcher (its Clusters list opens an entry of `workspace.json` through `desktop/switch.rs`, parking the one left; [ACCESS_IDENTITY.md](../ACCESS_IDENTITY.md#the-session-registry) has what a switch does to each thing), the location, Search everything, Refresh and Settings, a menu which holds the app version and, at its foot, All settings…. The Settings page (`Page::Settings`, `desktop/settings/`) is one page of seven sections (`SettingsSection`, `settings/sections.rs`), listed in its column under App (General, Connection, Monitoring, Coroot) and Workspace (Clusters, Argo CD destinations, Delivery sources); `FRESHKUBE_PAGE=settings-<section>` opens one, and All settings…, `⌘,` and the app menu's Settings… open the one shown last, Clusters at first. Monitoring still points to the header's menu until #697's slice 9 moves its controls. Coroot (`settings/coroot.rs`) is one Connection group on `freshkube_ui::form`: the server, how it signs in (`ui::segment`), the credential as a secret field (`Kept in <store>` with Replace… and Forget, never the value) and the project, with Connect and Revert at its foot. Connect writes the `coroot` block through `SetupFile::save_with` (the file's other parts and unknown keys kept; the key is named `keys.json` and Observability keeps it there as Connect starts, and only then does the block name it: `ObservabilityEvent::KeyKept` makes the section save `key: keys.json`, and until then the typed text stays in the field) and then emits `SettingsEvent::CorootConnect`, which the shell hands to Observability's `connect_from_settings`; a connect from Settings reads while Observability is hidden, so the group's state line, pushed back on `ObservabilityEvent::Connection`, says how it went. Disconnect emits `CorootDisconnect` and keeps the block, saving `coroot_reconnect: false` to `preferences.json`; Forget saves the block without its key and emits `CorootForget`. A broken or changed-on-disk file refuses the save with Clusters' words; example data shows an invented connection and saves nothing. Observability's connection card is one line, `Coroot isn't connected · Open Settings` (`ObservabilityEvent::OpenSettings`); once connected, its link panel (`Link Kubernetes cluster…`) stays. `coroot.json` is written only while no setup has been handed over. Clusters is a table of the clusters in `workspace.json` that Add, Edit, Remove and Move change and save at once (`settings/edit.rs`; never for example data). Argo CD destinations (`settings/destinations/`) is a list with its own toolbar and keys: Map adds a mapping from a server URL or Argo CD cluster name to one of those clusters, refusing one already mapped as Argo CD would match it, Edit changes one, and Remove asks first. The selection is the mapping's key, found again after a save or Reload, and a new mapping is selected once its save lands. A mapping whose cluster is gone is kept, marked with the Unknown ring, and left out of the status bar's count. Delivery sources (`settings/sources/`) lists which entry Kargo, the builds and Argo CD are read from (core's `workspace::Sources`: by role, or pinned under `sources` in `workspace.json`) and, as Workloads, every entry a destination maps to, each one's state counted. It reads nothing until Check sources, which reads one item of each part and each workloads entry through `delivery::entry` under its deadlines (Argo CD where its `part-of=argocd` workloads run); a new workspace or source, another section or leaving the page drops the check, and C does nothing while one runs. Each list's arrows stay in it. A list section's frame scrolls in a short window, its list keeping at least `SHORT_LIST_HEIGHT`; the three share the page's banners and its status bar line, and App's sections have no line. `PageId` keys every page in the page set's one map (`Pilot.pages.map`), and `PageId::SCREENS` lists the retained inspection panels independently of `Page`.

Overview derives its cards and attention rows when either summary changes (`presentation/overview/`, `presentation/attention/`), including independent unavailable parts. Attention groups its rows as Failing, Warning, then Unknown (last-known evidence from a stale source), with each group's count derived with the rows; it shows eight compact rows, and its showing bar expands them to at most fifty. Node panes use its rows for their own node, uncapped. The page is an entity of its own (`OverviewPage` in `desktop/overview/`): the shell hands it the cards and rows when it derives them and its state after each of its notifies, and it redraws only for a change; a card or row asks the shell through `OverviewEvent`. Object links use `Pilot::open_object`, which retains a matching namespace, and clears a hiding filter before navigating. Unknown UIDs are resolved through metadata-only reads, never full Secret reads.

The Kubernetes summary session (`kubernetes_summary/` in core and desktop) takes a `SubscriptionKey` (applied session/configuration revision, API, scope, selectors and retained representation) and serves only the exact summary key; the returned `Subscription` holds the shared publication and does not retain the key. Summary and visible Lifecycle share the same Node publication; the Resources printer-table watches remain separate. `InitDone` commits a complete replacement, including empty results. Failed or unfinished lists keep previous complete evidence explicitly stale; `Part::loaded()` can return that evidence, so check `is_current()` before inferring absence. A 403 remains `Part::Refused` and does not block other sources. Refresh cancels the watcher generation and relists; 410 relists the affected kind. Context/config replacement drops the `OwnedJob` and all child watches, while selecting a Talos node leaves the cluster session intact. Pods retain compact facts, at most 4 KiB each; object and byte limits fail visibly without evicting live records. Fixture input uses the same reducer with one captured reference time per session.

The shell's Kubernetes summary is session-owned: nine compact reflector stores run on every page and publish after a 500 ms coalescing window. Health and visible Lifecycle consume those observations; selecting a Talos node does not replace the session. The 15 s shell cycle and countdown are for Talos; metrics keep their separate polling schedules.
