# Settings

The behaviour of the Settings rail area: its ten sections, the shared form rules they follow and how they save to `freshkube.yaml`. The design is DESIGN.md's [The Settings page](../DESIGN.md#the-settings-page); the setup file's format, reload and migration are in [SETUP_FILE.md](../SETUP_FILE.md). Where this document and the code differ, the code wins. Written at main `2af002d`, after [#697](https://github.com/skel84/freshkube/issues/697)'s slices 1 to 10.

Code:

- `crates/freshkube-desktop/src/desktop/settings/` is the page. `mod.rs` holds `SettingsPage`, Clusters' table, banners and status, and `sections.rs` holds `SettingsSection`, `SettingsEvent` and General. Clusters also uses `source.rs` (the table), `form.rs` (the Add dialog), `edit.rs` (add, remove, move, the kubeconfig, `commit`, Reload), `kubeconfig_row.rs` and `entry/` (the Inspector's Identity and Metrics groups). The other sections are `connection.rs`, `monitoring.rs`, `coroot.rs`, `destinations/` and `sources/`.
- `crates/freshkube-desktop/src/setup_file/mod.rs` is `SetupFile`, the shell's owner of `freshkube.yaml`: its poll, `save_workspace` and `save_with`, the receipt and the file's problem. `desktop/startup/setup.rs` hands its changes to Settings and, through `Pages::set_setup`, its last good setup and safe problem text to Applications, and `desktop/shell/frame.rs` draws the receipt in the status bar.
- `crates/freshkube-ui/src/form.rs` draws groups, rows, errors, `SavedIn`, the secret field, path fields and the platform-ordered actions; `platform.rs` answers which side the default button takes.
- Monitoring's per-context source and Dashboards folder stay in `crates/freshkube-monitoring/src/page/` (`source.rs`, `settings.rs`, with `store.rs` for `monitoring.json`). Coroot's connection is `crates/freshkube-observability/src/connection.rs`, its one-line card `settings.rs` and its `coroot.json` `remember.rs`. Desktop routes the events between them (`desktop/entity_pages.rs`). General's Appearance and auto-refresh are saved by `desktop/shell/chrome.rs`, and text size by `freshkube-ui`'s `text_size.rs`.
- `crates/freshkube-core/src/setup/` parses and writes the setup file (`commit_with_backup`), and core's `secrets.rs` is `keys.json`.
- Core's `monitoring/scope::token_urls` names the setup's token accounts; Monitoring's `saved_token_urls` reads the context accounts through its typed store. Settings' `metrics_tokens.rs` removes a replaced token after a successful save, shared by Monitoring and the Clusters Inspector.

## The page and its sections

Settings is one `Page::Settings` with one `SettingsPage`, which shows one `SettingsSection` at a time. The rail has a Settings button, and its column (`shell/source.rs`, `settings_lines`) lists the sections in two groups: *App* (General, Connection, Monitoring, Coroot, Notifications, Audit log) and *Workspace* (Clusters, Argo CD destinations, Delivery sources). Each row is `nav-settings-<slug>` and is current while its section shows. Each section is also a page slug, `settings-<slug>`, for `FRESHKUBE_PAGE`; a bare `settings` opens Clusters, the default. `OpenSettings` (⌘, on macOS; Windows and Linux bind no key, since Control-, is the dock's) and the gear's "All settings…" open the section shown last, which the page holds for the session and doesn't save.

The header's gear keeps only "Quick controls": Talos auto-refresh, Appearance and Text size, the same preferences as General. Below them, "All settings…" closes the popover and opens the area.

App sections are padded forms. Settings dialogs use `freshkube_ui::dialog::frame`: Kit caps the surface to the window and scrolls its body, with the title and the platform-ordered actions in its fixed header and footer.

Workspace sections are table pages: Clusters and Delivery sources hold the selection in the shared Inspector, while Argo CD destinations edits in a dialog. Only the three lists put a segment in the status bar. Delivery sources' check runs only while its section shows: leaving the section, or the page, drops a check in flight. When the setup has `delivery.stage_naming` ([#804](https://github.com/skel84/freshkube/issues/804)), Delivery sources also lists a read-only Stage naming row (`sources/rows.rs`, `Read::StageNaming`): the template, and whether a Stage is named by project key or by name only. It is read from the file, so Check sources doesn't touch it, and it is edited in `freshkube.yaml` only.

**Where a section is saved.** Every group ends with one muted line from `form::SavedIn`, naming the file, and the store when a key goes elsewhere:

| Section | Saved-in line |
| --- | --- |
| General | `Saved in preferences.json`, or `Not saved; resets at launch` without a preferences folder (`--fixture` has none) |
| Connection | Talos: `Saved in connection.json`, or `Not saved; resets at launch` with example data or no preferences. Kubernetes API: always `Not saved; resets at launch`. Kubernetes-only launches: `Saved in connection.json` once a file is remembered |
| Monitoring | Metrics source: `Saved in freshkube.yaml`, or `Saved in freshkube.yaml; the token in keys.json`. This context: `Saved in monitoring.json`, with `; the token in keys.json` for a token |
| Coroot | `Saved in freshkube.yaml, the key in keys.json`, or `Saved in freshkube.yaml` for Anonymous or a key file; `Not saved; resets at launch` in example data |
| Clusters | Each Inspector group: `Saved in freshkube.yaml` |
| Argo CD destinations | The dialog: `Saved in freshkube.yaml` |
| Delivery sources | Routing: `Saved in freshkube.yaml · sources` |

## The shared form rules

`freshkube_ui::form` draws a section's groups; the page owns the drafts, the checks and the saving.

- **Save and Revert.** A group of linked fields (Connection's Talos group, Monitoring's Metrics source, Coroot's Connection, each Clusters Inspector group) has a pair at its foot. The default button trails on macOS and Linux (Revert, Save) and leads on Windows (Save, Revert); dialogs order Cancel the same way. Save is off while the group is clean or can't be saved, and Revert while it is clean. Return in a field presses the group's default button, and Escape reverts a changed group once. A changed group draws an accent `•` after its heading. A choice that stands alone saves at once: Appearance, Text size, auto-refresh, the workspace's kubeconfig, the Dashboards folder, a pin, and Clusters' Add, Remove and Move. The Kubernetes API's mode applies at once and isn't saved.
- **Leaving a section.** The shell's one guard (`desktop/shell/settings_guard.rs`) covers the Settings column, the sidebar and page shortcuts. Sections opt in through `SettingsPage::has_unsaved`, `save_unsaved` and `discard_unsaved` (`settings/unsaved.rs`): Connection's Talos draft, Monitoring's Metrics source and per-context source, Coroot's Connection and Clusters' Inspector groups. A changed section's column row shows the same accent dot as its group, named “Unsaved changes”. The Kit dialog offers Save, Discard and Stay. Save validates and waits for saving, including Coroot's typed key, before opening the requested destination; a validation or write failure keeps the section and draft. Discard restores the saved values before leaving. Stay, Escape and closing the dialog keep editing. A clean section and General's immediately saved choices never prompt. The Clusters Inspector retains its own selection/Add guard within the section.
- **Inline errors.** A field is checked when it loses the keyboard, and the whole group on Save (and on Monitoring's Test). Shared form rows that call `.error(...)`, including with `None`, reserve a message line even without a hint, so showing an error leaves the next row in place. Every checked row in the shipped forms has a hint explaining its input, including Monitoring's Central and per-context fields and the destination dialog's Workspace cluster; the blank reserve is a safety net. Rows that are never checked add no empty line. The error replaces the field's hint, in `crit_ink`, and the input's border turns `crit`. Save then moves the keyboard to the first failing field, top to bottom, and writes nothing; Connection, Clusters, Monitoring and the destination dialog do this. A refusal no field explains shows in a banner: Clusters' Inspector puts it at its top, Monitoring in a "Not saved" banner.
- **Locked fields.** A section that can't save says why and changes nothing. With example data, without a preferences folder, or while `freshkube.yaml` is broken or changed on disk, Clusters' Inspector disables every field, choice and Browse… and shows one of "Example data isn’t saved", "This window keeps no preferences, so there is nowhere to save", "freshkube.yaml isn't usable. Nothing was written; fix the file and reload." or the changed-on-disk words below. Monitoring disables Save and puts the reason in the mode's hint; Coroot disables every control in example data and refuses a save over a broken file with the same words; the lists' actions are off, with the reason in their tooltips. Connection's example data disables the Talos inputs and Browse… ("Example data doesn’t read a talosconfig.") and the Kubernetes API's choices.
- **The style checks.** `scripts/check-style.sh`'s `label` rule fails a hand-drawn 12.5 semibold label outside `form`, and its `buttons` rule fails a hand-placed Revert, Discard or dialog Cancel, so every group and dialog takes the platform order from `form::actions`. #697's pending entries are gone.

## General

Two groups. *Display*: Appearance (System, Light, Dark), which runs the app menu's appearance actions, and Text size, one button per step from 12 to 20 ("Size in pixels; keyboard shortcuts also change it."). *Refresh*: the Talos auto-refresh switch, off without Talos; its hint says whether Talos refreshes every 15 s, is off, or needs a Talos connection, and that Kubernetes updates are watched. Each choice saves at once in `preferences.json` (`appearance`, `talos_auto_refresh` and `text_size`), keeping the others and any unknown keys, and applies at the next launch. `FRESHKUBE_THEME` and `FRESHKUBE_TEXT_SIZE` override them for one debug session without saving.

## Connection

*Talos*: the talosconfig, a path field with Browse… (Browse clears the context), and its context, empty for the file's current one. Blur checks the draft by reading the file's contexts (a `Loader`): an unreadable file puts its error on the path, and a context the file lacks says "Choose a context that is in this talosconfig." Save applies the file to the connection and remembers it in `connection.json`; an invalid draft leaves the applied connection as it was.

*Kubernetes API*, while Talos is connected: Automatic, From Talos, or File with its kubeconfig (Browse…) and a context list with the current one tagged. A choice applies at once, File once its file has a known context, and none is remembered. A Kubernetes-only launch shows its kubeconfig files with Browse… instead.

## Clusters

A table page of the workspace's entries, in file order with no sort: an unlabelled status column, Cluster (the id), Role, Context and Talosconfig. The status column shows a Warn mark when an entry did not open as defined, and the row's tooltip adds the note. With no file the table is empty, and the status bar counts the one cluster this window opened as an implicit workspace of one.

- **Toolbar, keys and row menu.** Add (`a`), Edit (Enter or `e`), Remove (Backspace), Move up and Move down (⌘⌥↑ and ⌘⌥↓, Control-Alt on Windows and Linux) and Reload (`r`); ↑ and ↓ move the selection, and Escape clears it. Edit opens no dialog: it puts the keyboard in the Inspector's Context field. The row menu holds Edit, Remove, Move up and Move down. A right-click selects the row and opens its menu at once; when no Inspector was open, it waits until the menu closes to open, keeping the row's popup in place.
- **Add** is a small dialog, "Add a cluster": Role (Core, CI/CD, Environment; Environment by default) and the kubeconfig Context. The id is derived from the context (`Workspace::fresh_id`: lower case, other characters to `-`, `-2` and on for a taken one). The dialog stays open with what was typed if the save fails, and selects the new row once saved.
- **Remove** asks first, "Remove {id}?": it takes the entry out of `freshkube.yaml` and touches nothing on the cluster or in any kubeconfig or talosconfig, and says when Argo CD destinations stay mapped to it, marked. It drops the entry's unsaved Inspector changes without asking.
- **The kubeconfig row**, in the header's second line, shows the workspace's `kubeconfig` path or "Automatic: KUBECONFIG, then the home default". Browse… chooses a file, never edits it, and Use automatic clears it; each saves at once.
- **The Inspector**, beside the table or under it on a narrow page (`inspector::split`), is headed by the selected entry's id and holds two groups. Its shared body keeps padding outside the scroll, so scrolled lines stay clear of the heading; selecting another entry resets the body to the top. In a small window the stacked panes fit the page, keeping the toolbar and column header outside the Inspector's scroll:
  - *Identity*: Role, Context, the talosconfig (a path field whose Browse… fills the draft), and the Talos context. Errors: an empty context, a talosconfig that isn't an absolute path, a Talos context without a talosconfig.
  - *Metrics*: the label value, the entry's value of the central store's label (its id unless set), and its own store, None, Service (namespace, Service, port, reached through this cluster's API server) or URL ("A store of its own wins under any mode."). A URL's token is never shown; a URL save keeps it, and choosing Service or None drops it from the block. After the YAML write succeeds, the replaced token is removed from `keys.json` unless another setup store or a context in `monitoring.json` still names that account.
  - Each Save writes only that entry's keys through `SetupFile::save_workspace`, keeping the rest of the setup and its unknown keys.
- **Save, Discard or Stay.** Changing the selection (click, arrows, Escape, the row menu) or pressing Add while an Inspector group has changes asks through the platform's prompt (`window.prompt`): "Save the changes to {id}?", with Save, Discard and Stay. Save writes the groups first and stays on the entry if a field fails. Reload doesn't ask: it rebases the drafts on the file read again, and drops them only when a change on disk was waiting.
- **Status.** "{n} clusters · {m} destinations mapped · freshkube.yaml · Kubeconfig: …" ("Example workspace" with example data; a part that would say 0 destinations is left out), or "1 cluster · implicit: the one this window opened".

## Monitoring

Three groups.

- **Metrics source**, the setup file's `metrics` ([SETUP_FILE.md](../SETUP_FILE.md#metrics)): one choice as a segment, Automatic, Central or Per entry. Automatic has no fields. Per entry explains "Each entry names its own source in freshkube.yaml." and follows it with an "Edit it in Clusters" link, which goes to Settings → Clusters and selects the first entry in file order, so its Inspector's Metrics group shows; an empty workspace opens the empty table. Switching selection keeps the Inspector's Save, Discard or Stay guard. Central chooses a store, a Service (the hosting entry, namespace, Service, port, HTTPS, path) or a URL with its token, then the cluster label (a Prometheus label name). Save writes only `setup.metrics` through `SetupFile::save_with`.
  - **The token** is a secret field: once saved, "Kept in keys.json" with Replace… and Forget, never its value; a changed URL asks for its own token. Save puts a typed token in `keys.json` (account `Prometheus <url>`) before it writes the YAML; a refused write restores the previous token, or removes the new one. Switching to Service, changing the URL or Forget removes the old token only after the YAML write succeeds and only when no other setup store or per-context source in `monitoring.json` names that account with a token. Equivalent URL spellings share an account. A store retained under Automatic or Per entry still names its token, so changing only the mode keeps it. An unreadable `monitoring.json` keeps the token and says that the setup was saved but its context references could not be checked. A token-removal failure says that the setup was saved but the token could not be removed.
  - **Test** checks the unsaved values against the open entry, read-only, and answers "Passed", "Failed" or "Unknown" with why (no workspace entry open, no Kubernetes connection for the entry or the hosting entry), or times out after 45 s. Once validation passes, the keyboard returns to the form, clearing the button's focus appearance without taking focus again when the check finishes. A changed draft or a hidden section drops the check.
  - **Check entries** (Central only, beside Test; `settings/labels.rs`, `scope::label_counts` and `entry_labels`) asks the store one query, `count by (<label>) (up)`, and lists an "Entries in the store" group with a line per entry: the value it reads has N series, has none now (Unknown, never Failed, as Test says it), or it reads its own store and is not checked. When an entry's value has none, its context name has series and no entry reads that name, the line suggests `metrics.value: <context>`; values with series that no entry reads are named in one line (at most 20) and none is suggested. It checks the saved setup, so it is off while the group has unsaved changes ("Save the Metrics source first"); it starts only from the button while the section shows, and hiding drops it. Select a line and Accept (Enter or `a`, or the group's button) sets only that entry's `metrics.value` through the page's save, refused as any save is; Ignore (Backspace) writes nothing and lasts for the session. A refused or failed store says so and suggests nothing. The selected line is drawn as the table draws a selected row (`form::Row::selected`: the soft accent fill and border across label and value). Example data answers at once from `example_label_counts` and cannot accept; `FRESHKUBE_METRICS_LABELS=capped` makes that answer cut at its cap, so the capped wording and the "not among the values read" line show.
- **This context.** A context that is a workspace entry, or example data, says that the setup file decides its source. Any other context keeps Monitoring's own choice, Automatic, Service or URL, with its own read-only Test, which also returns the keyboard to its form; Save writes it to `monitoring.json` and its token to `keys.json`. Replacing its URL or Forget keeps an account still named by the setup or another context with a token.
- **Dashboards folder**: the folder or "None", with Choose… and Forget, each saved at once in `monitoring.json`; off with example data. The Monitoring column's "Choose a folder" opens this section scrolled to the folder group, including when Central's fields extend below the window.

Example data shows the example setup's metrics; Save, Test and Revert do nothing. What the Monitoring page does with the scope it saves is in [monitoring.md](monitoring.md).

## Coroot

One *Connection* group: the server, how to sign in (API key, Session, Anonymous), the credential (hidden for Anonymous; "API key" or "Session value", a secret field kept in `keys.json`, or "Read from the key file named in freshkube.yaml" when the block names an `api_key_file`), the project (optional), and a Status line: the save's error, else Observability's failure, "Connecting…", "Connected to {server}" or "Not connected", with Disconnect while connected. The group's default button is labelled Connect.

- **Connect** checks the fields, then writes the `coroot` block through `SetupFile::save_with` over the file's own block, keeping its unknown keys (an unchanged block isn't written), and asks Observability to connect (`SettingsEvent::Connect`, routed by `entity_pages.rs`). Observability stores a typed key in `keys.json` (account `Coroot <url>`) at once, whether or not the connect then works; once it is stored, the block gets `key: keys.json` and the field lets the key go. With nothing typed, Connect reads the stored key or the key file.
- **Disconnect** keeps the block and saves `coroot_reconnect: false` in `preferences.json`, so the next launch doesn't connect.
- **Forget** removes `key` from the block, then drops the stored key from `keys.json`.
- **`coroot.json`** is written only while no setup has been handed over; once a setup is in use, the connection lives in `freshkube.yaml`.
- **Example data** shows the example connection with every control off and saves nothing; a window without preferences has nowhere to save.

Observability no longer holds the connection: with none, its card is one line, "Coroot isn't connected · Open Settings", which opens this section (`ObservabilityEvent::OpenSettings`). The header's Coroot button opens this section when nothing is connected, and the link panel, with Open Settings, when connected. The link panel also says which Coroot cluster the open entry's Kubernetes links read, or why it has none; that is `clusters[].coroot` in the setup file (`freshkube-observability`'s `entry.rs`), edited by hand until the Clusters Inspector's Observability group exists.

## Notifications

`desktop/settings/notifications.rs`. An immediate-save form over the app's `Followed` owner ([followed.md](followed.md)), saved in `follows.json` beside the preferences as each control changes: **Group updates** (on by default), **Quiet hours** (off by default; a start and an end in half hours, and failures still come through), **Hide details** (Default is on for protected and read-only clusters, On, Off), and **Followed**, every followed item with what it reads, when it ends and its state, and Stop. A follow that can't be read says "Not watching" and why. The macOS permission row arrives with banners.

## Audit log

A read-only page (`desktop/settings/audit.rs`) over the app's two audit logs, across contexts, newest first: the writes the app sent to Kubernetes objects (`<preferences>/audit/writes.jsonl`, [WRITE_MODEL.md](../WRITE_MODEL.md#the-audit-log)) and Talos Operations' files (`~/.freshkube/operations-*.yaml`). A **Source** filter (All, Writes, Operations) narrows the rows. Each row has the time, the source, the context, the action, the object and the phase, and under it the result and, for a write, the field paths it changed. It records field paths only; no value, credential or Secret value is in either log, and none is shown. At most the newest 200 rows are drawn and the rest are counted. A line or file that cannot be read is said (`audit-unreadable`), never hidden. The files are read off the UI thread when the section shows and not while the page is hidden; example data shows invented rows and reads nothing. Nothing on the page writes. Tests: `desktop/settings/audit_tests.rs`.

## Argo CD destinations

A table page of the workspace's `destinations`: a status column, Destination, Match by (Server URL or Cluster name) and Workspace cluster. Map (`a`), Edit (Enter or `e`) and Remove (Backspace) run from the toolbar, the keys and the row menu; Map and Edit need a workspace cluster. Map and Edit open a dialog with one *Mapping* group: Match by, the value (`spec.destination.server` or `.name`) and the workspace cluster, a searchable select. The value is checked on blur (empty, not an http or https address, already mapped), and Save focuses the first invalid field. `https://kubernetes.default.svc` and exact `in-cluster` are accepted for the selected Argo CD source entry: the explicit pin, otherwise the first Core entry in file order. A conflicting target or an undetermined host is an error on the workspace cluster field; the same core check protects the file read and write paths. Remove asks first. A mapping whose cluster the workspace no longer lists shows the Unknown mark and says to edit it. Every change saves to `freshkube.yaml` through the page's `commit`, with Clusters' refusals.

**Find suggestions** (the toolbar, `f` or the row menu; `destinations/suggest.rs`, `freshkube-delivery`'s `discover/`) reads Argo CD's cluster Secrets (`argocd.argoproj.io/secret-type=cluster`, one page of 100 per Argo CD namespace) through the Argo CD source entry, matches each Secret's `server` to the contexts of the workspace's kubeconfig, and lists what it found in a "Suggested · n" group under the mapped rows, with a Found from column. It starts only from the button while the section shows, never on show, under a 30 s deadline; hiding the section drops it and a late answer never lands. The findings are kept, and the items are derived from them and the setup whenever either changes, so a save, a Reload or a hand edit never reads again. Findings for another source, kubeconfig or example mode are dropped.

- **Matching.** Servers compare through `normalize_server` (case, a trailing `/` and `:443` on https are ignored; the path is kept). The contexts that match become workspace entries by `entry.context`: one entry is a suggestion (`server` and, with a name, `name` rows), several are Ambiguous, a context no entry opens says to add it in Clusters, and no context says "no kubeconfig context has this server". A server already mapped gives no item. Argo CD's own cluster (`https://kubernetes.default.svc`, `in-cluster`) is made up from the Argo CD source entry, never compared with a kubeconfig server, and joined by any Secret naming that address.
- **Accept** (Enter or `a` on a suggestion, the toolbar, the row menu) re-derives the item against the page's workspace and saves the mappings through `commit`, so it is refused as any other save is (example data, no preferences, a broken or changed file, which leaves the item listed). **Ignore** (Backspace, the toolbar, the row menu) writes nothing: the item's key joins `SettingsPage::ignored` for the session, and the status bar counts it.
- **The Secret read** keeps only each Secret's name, `data.server` and `data.name`. `Reader::cluster_secrets` is the one door that reads Secrets: raw `send`, the body parsed into three-field structs and dropped before the function returns, never through `Api<Secret>`, never formatted or logged, and a parse failure says fixed words. A refused, capped or failed list suggests nothing from itself and says so in a note. Reading needs `list secrets` in Argo CD's namespaces; RBAC cannot narrow a Secret list by label.

## Delivery sources

A table page with one row per part, Kargo, Builds and Argo CD, then Workloads, read on every entry a destination maps to: a status column, Part, Entry, Chosen by (Pinned, the role, Workspace of one, No entry with that role, or Pinned, not listed), State and Reads. While `freshkube.yaml` has a fatal problem, a "Setup file" row says it isn't used. Accepted row recovery keeps that row as "Used with warnings" in Warn tone, with every skipped row’s safe reason. An all-skipped cluster list has unavailable sources instead of the open connection. Its empty Clusters table says every configured cluster was skipped and asks for repair and Reload, matching the status bar’s zero clusters; an intentionally empty setup keeps the implicit-cluster explanation. A role whose original selected row was skipped remains unavailable, naming that row rather than choosing a later cluster.

- **Check sources** (the toolbar, `c` or the row menu) reads each part where it is chosen, through a `Loader` keyed on the sources, the kubeconfig, the open connection and example data, with a 30 s deadline. The table shows loading rows meanwhile, and the status bar says "Last checked HH:MM" once it lands. States: Not checked, Reading, Readable, Refused, Not served, Unreachable and Not in the workspace. Example data answers at once.
- **The Inspector** says why a part is read where it is (Chosen by, State, Reads) and holds its *Routing*: Pin to entry… and Follow roles, also in the row menu. A pin saves at once in `freshkube.yaml`'s `sources`, keeping the other parts and unknown keys, and is refused in example data, without preferences, or while the file is broken or changed.

**Find suggestions** (the toolbar, `f` or the row menu; `sources/suggest.rs`, `freshkube-delivery`'s `discover/builds.rs`) counts the PipelineRuns on the Builds entry by namespace, from one metadata-only list across the cluster (`Reader::namespace_counts`, at most 2,000 items, only `metadata.namespace` kept), and offers `delivery.build_namespace` in a "Suggested · 1" group with its evidence (every namespace that holds runs, with its count) in the Inspector. It starts only from the button while the section shows, never on show, under a 30 s deadline; hiding drops it and a late answer never lands. The suggestion is derived from the findings and the setup's current value whenever either changes, so a save, a Reload or a hand edit never reads again.

- **What it says.** Kargo's Projects are listed by name through the Kargo entry (cluster-scoped, names only, at most `MAX_PAGES` × `PAGE_LIMIT`). Every namespace that contains a project's name gives a candidate `{project}` template (`shop-ci` → `{project}-ci`), kept only when #820's `resolve_build_namespace` accepts it; its fit is the projects whose resolved namespace holds runs. The best template that fits at least two projects is suggested. Projects with no runs in their namespace are listed (their changes find builds by commit only, as before), and namespaces with runs that the template names for no project are listed as unexplained: the fit is then Partial, Warn tone, and Accept is kept. Two templates that fit equally are shown as a Tie and neither is chosen. With no template: all runs in one namespace and the list not cut suggests that namespace; runs in several namespaces list the busiest ten and suggest none.
- **Where a name sits.** Every position of a project's name in a namespace gives a candidate (`app-app` gives `{project}-app` and `app-{project}`); a name inside another word (`api` in `rapid`) is only a candidate, and counts as a fit only for a project whose resolved namespace holds runs, so one such fit is never a template.
- **A cut run list** (more than 2,000 PipelineRuns; the list is not asked from the API server's cache, so it is cut) never suggests a single namespace. The two best candidates from the part that was read are confirmed by one `limit=1` read (`Reader::any_in`) of each project's namespace, at most 50 projects, so a tie between them shows; the unexplained namespaces then read "at least", and a third candidate is said not to have been compared. A namespace that couldn't be checked is named in a Warn note and nothing is suggested. With more than 50 projects the item is Capped and suggests nothing.
- **Existing value.** When Kargo's projects weren't read and the value is a `{project}` template that still names namespaces with runs, nothing is suggested and the note says so. A value that already equals the suggestion gives no item; a plain value whose namespace holds no runs is said ("delivery.build_namespace is ci, which holds no PipelineRuns"). A refused, unserved, unreachable or failed list suggests nothing and says why in a note; Kargo's projects not being read says so and leaves the plain rules.
- **The Inspector** shows the evidence: every namespace with its run count, and for a template the projects that fit, those with no runs and the unexplained namespaces.
- **Accept** (Enter or `a` on the suggestion, the toolbar, the row menu) sets only `delivery.build_namespace` through `SetupFile::save_with`, keeping the rest of `delivery` and the setup, and is refused as any save is (example data, no preferences, a broken or changed file, which leaves the item listed). A saved value shows as a read-only "Build namespace" row. **Ignore** (Backspace) writes nothing and lasts for the session; the status bar counts it.

## The setup file's saves

Every workspace section, Monitoring's metrics and Coroot save through `SetupFile` (`save_workspace` calls `save_with`), which edits a copy of the last good setup, writes it off the UI thread and keeps every part it wasn't asked to change, unknown keys included.

- **Refusals.** While row warnings remain, Settings says "Fix the skipped items in freshkube.yaml and Reload before saving from Settings." and writes nothing, preserving skipped rows and their unknown keys. The file is read again just before the write. A file changed since it was read refuses the save with "freshkube.yaml changed on disk since it was read. Nothing was written; reload to see the file as it is." A file that doesn't parse refuses every save: "freshkube.yaml isn't usable. Nothing was written." Nothing is ever written over it.
- **`.bak`.** When the file on disk isn't the app's own last write, so it was edited by hand, the save first copies it to `freshkube.yaml.bak` (`commit_with_backup`), replacing an older backup; a backup that can't be written leaves the setup file alone.
- **The receipt.** A save sets `SetupFile`'s receipt, and an outside change read by the poll sets "Reloaded". The status bar shows it on every page as "Saved · backup .bak · 14:02" for a save that made a backup, "Saved · 14:02" for a later save without one, or "Reloaded · 14:02" (`setup-reload-status`). The accessible label and tooltip keep the full text: "Saved freshkube.yaml · 14:02", plus " · the hand-edited file is freshkube.yaml.bak" when a backup was made. A file problem or a missing file clears it, and it hides while an unsaved edit is stale.
- **Banners.** Clusters, Argo CD destinations, Delivery sources and Coroot draw the page's banners (`render_banners`): "Workspace file not used" for a `workspace.json` that couldn't be migrated, "Setup file" for `freshkube.yaml`'s fatal problem, "Some rows in freshkube.yaml skipped" for accepted row recovery, "Unsaved edit is stale", "Unknown keys" (at most five named, then how many more), "Not saved" (Crit) with the save's error, and "Saved" (Good). "Saved" repeats what the last save through the page's `commit` did (an entry added, changed, moved or removed, a mapping, a pin) with the receipt, "Added cluster-b. Saved freshkube.yaml · 14:02", and clears on a section change, Reload, a change on disk or a problem.
- **An outside edit.** `SetupFile` polls the file every 2 seconds ([SETUP_FILE.md](../SETUP_FILE.md#reload-on-change)). While a dialog is open, a save runs, or a Clusters Inspector group has changes, a change waits behind "freshkube.yaml changed on disk. Reload to drop the unsaved changes."; otherwise the page takes it at once. Monitoring's and Coroot's drafts don't hold it back.

## Team setup

Settings › Workspace › Team setup (`settings-team`, `desktop/settings/team.rs`) is where a person joins a team's shared `freshkube.yaml` ([#849](https://github.com/skel84/freshkube/issues/849)). The rules are core's `team` module (`crates/freshkube-core/src/team/`), which has no UI types and runs nothing; the page draws them. Tests: core's `team/tests.rs` and `desktop/settings/team_tests.rs`.

**The page** shows the source, the applied version, the ignored keys, "Your values over the team’s" (each of the person's own values, with the team's beside it, or "Held at the team’s level" for a looser protection override), a failure banner, the review and the Leave choices. The review's rows keep a short label (the kind of trust change) and a one-line value with the whole of it on hover. "Review later" puts the review off behind a "A new team version waits" banner with a Review button; what was confirmed stays confirmed. The banner counts what is left to confirm; with no trust change it says how many settings will change, and once every trust change is confirmed it says "All 4 trust changes are confirmed. Apply to use version …". A row's label is at most 20 characters, since the label column is fixed; a value's tooltip is the shared `FollowTooltip`, which hides when a scroll moves the line from under the pointer. Its icon is `Users`, embedded in `ExtraIcons`.

**Slice 1 runs on example data.** Nothing is fetched and nothing is written to the person's `freshkube.yaml` yet. `--fixture` plays `FRESHKUBE_TEAM` (`none`, the default, `joined`, `update`, `trust`, `failed`); without `--fixture` the section says "Not in a team".

- **Source** (`team/source.rs`). A git repository (`https://`, `ssh://` or `git@host:path`, a branch or tag, a path in it) or an HTTPS address. Plain HTTP, `file://`, `ext::`, a local path, an address with a password (or any user info on `https://`), an address with a query or a fragment, a host or user that starts with `-`, a ref that starts with `-` and a path with `..` are refused, and the refusal never repeats the address. `redact` drops user info, query and fragment from every address a log, an error, `Debug` output or the page shows; a token never goes on a command line, in an address or in a log. An HTTPS fetch follows a redirect only to HTTPS on the same host and port (`check_redirect`); its optional token is kept in the key store under the account `Team setup <origin>`.
- **Fetching runs nothing from the repo.** `GitFetch` describes the person's own `git`. Every flag is listed in a test: `GIT_TERMINAL_PROMPT=0`, `core.hooksPath` set to an empty directory, `protocol.allow=never` with `protocol.https.allow=always` and `protocol.ssh.allow=always` (so a `url.insteadOf` can't rewrite an address to `http` or `git`), `http.followRedirects=false`, `protocol.file.allow=never`, `protocol.ext.allow=never`, `submodule.recurse=false`, `--no-recurse-submodules`, `--no-tags`, and the address after `--`, into one fixed ref (`refs/freshkube/team`) of an app-owned mirror. No credential is stored; `-c credential.helper=` is added only when the token comes from our key store, otherwise the person's helper is left alone. The file is read with `git cat-file blob refs/freshkube/team:<path>`, the raw blob, so no `textconv` or filter driver runs. Slice 1 builds and tests the command and does not run it: the `Fetch` trait's only implementation is `example::FakeFetch`, and nothing reads the network.
- **What the team file may set** (`team/file.rs`). The file is read as plain YAML because it never names a context, against an **allowlist** of the keys a team may set (clusters' `role`, `protection`, `fingerprint`, `coroot`, `metrics` and `results`; `coroot`, `supply_chain`, `metrics`, `delivery` and `sources`). Everything else is named in `Version::ignored` and left out, never an error: contexts, local paths (`kubeconfig`, `talosconfig`, `ca_file`, `api_key_file`), keys and tokens, `agent` access, `writes` and `write_model`, notification and follow settings, history, `destinations` (the person's own mapping), a key that isn't on the list and a value of the wrong shape. A map key that contains `.`, `[`, `]` or `:` is ignored (`BadKey`), so no key can address another path (`agent.enabled`, `clusters[a].protection`); a cluster id may use only letters, digits, `-` and `_`, and a bad id refuses the file without repeating it. A key file (`supply_chain.public_key_file`) may live in the repo: `resolve_in_repo` refuses an absolute path, a `..` and a symlink that leaves the checkout.
- **Which value wins** (`team/merge.rs`). Yours over the team's over the defaults; `Origin` says which, and `Yours · over the team’s` offers "Use the team's value". **Protection is the exception:** the team's level is a floor, kept by `resolve` every time the merge is read. A cluster the team names with no level has a floor of guarded; a cluster it doesn't name has none. An unknown level counts as guarded, in the team's value and in yours, as the write model does. A team that tightens raises a looser override of yours. `allowed_levels` is the floor and the stricter levels, so the Inspector can say why the looser ones are off (`floor_words`).
- **Review** (`team/review.rs`). A fetched version waits in `Membership::pending` and never applies unreviewed, a team cannot opt out, and the first version is reviewed too. A `Review` has two steps: trust changes first, then the rest. **Every setting that changes is a trust change unless it is on a short safe list** (`role`, `coroot.project` and `coroot.cluster`, `metrics.value` and `metrics.label`, `delivery.build_namespace` and `delivery.stage_naming.*`, and a cluster appearing or going), plus a signing key fingerprint and any **floor that got looser**: protection is judged by `merge::floor` before against after, where no floor is the loosest, so a level that loosens, a level that goes, and a team that stops naming a cluster that had a floor (a named cluster with no level has guarded) each need a confirmation, one per cluster. Stopping to set a key counts. **Each trust change is confirmed on its own** (`Review::confirm_trust`); the rest can't be confirmed (`confirm_rest`) while one waits. Only `Membership` makes a review, the fields of `Membership`, `Review`, `Version` (`Version::parse` is its only constructor, so the allowlist and the id check can't be skipped), `GitSource` and `HttpsSource` (`new` is theirs) are private, and `Membership::apply` refuses a review that isn't of the current applied and waiting versions (`NotReviewed::Stale`) or isn't fully confirmed. The page says why in a banner (`NotReviewed`'s words) and makes the review again from the waiting version.
- **When it can't fetch.** A fetch or parse failure keeps the applied version, and `Failure` says since when and why. A later good fetch clears it.
- **Leaving** (`Membership::leave`). "Leave and keep a copy" saves the team's values as the person's own; "Leave and go back" returns the overrides from before joining. Slice 1 ends the membership in the example and returns the overrides; saving them is slice 2.

Left for later slices: running git and HTTPS for real and a reload schedule, joining and "Map your contexts" from the app, saving overrides to the person's `freshkube.yaml`, the Team and Yours chips on the Clusters rows and every Inspector field, the Settings banner and status-bar item for a waiting version, and applying a reviewed version to the live setup revision (reads restart, pages stay put). When key files come through git objects, tree entries of mode 120000 (symlinks) must be refused.
