# Database explorer

Code: `freshkube-db` (`crates/freshkube-db/src/`) is the session, with no GPUI and nothing of desktop: `postgres.rs` (the read-only Postgres session), `readonly.rs` (the statement check), `limits.rs` (timeouts and row cap), `wire.rs` (the `tokio-postgres` connection under it), `session.rs` (the `Session` trait and its types), `credentials.rs` (the in-memory password) and `fake.rs` (the example `shop` database and a recording fake server), `statements.rs` (where the statements of an editor's text are). `freshkube-core`'s `databases/explore.rs` picks the pod and reads the login. `freshkube-desktop/src/screens/databases/explore/` is the tab: `mod.rs` (the connection), `browser.rs` (schemas and tables), `data.rs` (a table's rows and the record Inspector), `view.rs` and `fail.rs` (the connect step's states). The Query tab is `freshkube-desktop/src/desktop/dock/query/`: `mod.rs` (runs, Cancel), `results.rs` (a result per statement), `history.rs` and `view.rs`; `screens/databases/query_link.rs` is what the explorer hands the dock. Design and slices: [#948](https://github.com/skel84/freshkube/issues/948). Tests: the unit tests in each `freshkube-db` module, core's `databases::explore::tests` and desktop's `explore/tests.rs`.

This is slices E1 and E2: PostgreSQL by CloudNativePG, read-only, through a port forward, with the explorer and the Query dock tab. Teleport (E3), the `databases:` block of Team setup (E4), MySQL and MariaDB (E5) and writes (E7) are later; until E4 the row cap (200) and the timeouts are built in.

## Opening it

**Explore** on a Databases row (the toolbar, the row menu, `E`) opens one tab per database beside the inventory's Clusters, Backups and Schedules views; it is not a rail area. Only a CloudNativePG database can be explored; MariaDB says so. Closing the tab closes the connection and stops the forward it started. Changing the connection (cluster) closes every explorer tab.

## Connecting

Four steps, each a state the tab can stay in, with words that say what to do:

1. **Choose a pod** from the Cluster's instances: a ready replica by default (first by name), else the ready primary. *No pod is ready* otherwise.
2. **Forward to it** through the app's `ForwardList` ([PORT_FORWARD.md](../PORT_FORWARD.md)): a pod forward tied to the pod's UID, on an automatic local port, port 5432. It appears in the status bar like any forward, and ends with the tab. *The forward failed* carries the forward's reason.
3. **Read the login and connect.** The team's reader Secret comes first (the name arrives with E4; until then none is named), then the operator's application user (`<cluster>-app`). The superuser Secret is never read or offered. *No reader Secret* when neither exists; *The Secret has no login* when it lacks a username or password.
4. **Make the session read-only** and verify it. *The database refused the connection*, *did not answer in time*, *could not be reached*, and *The session could not be made read-only* are the other outcomes. A failed connection offers Try again; nothing retries by itself.

### The Secret

This is the one place Databases reads a Secret. It is read **once per connection**, inside the connect job after the forward listens, through core's `databases::explore::read_login` (the explicit call site), and goes straight into a zeroizing in-memory `Password` (`Login` in core): no `Display`, `Clone` or `Serialize`, and a `Debug` that prints `<redacted>`. Only the username, password and database name are taken from the Secret; its other keys (connection strings that embed the password) are dropped at once. The password is never logged, never in an error, history, the audit log, the document, Search, a deep link or a saved file, and it is dropped (wiped) when the connection is made. Tests assert it is absent from the `Debug`/`to_string()` of a failed connect, the connect states and `Connected`.

**The superuser is refused, not just not offered.** A reader input or app Secret named `<cluster>-superuser`, or the Secret the Cluster's `spec.superuserSecret` names, is refused before any Secret is read; so is any login whose username is `postgres`, whatever its Secret is called. (The Cluster object is read for that spec field, as it is for `serverCASecret`.)

**One more read: the CA's certificate.** To check the server's certificate, core reads the cluster's CA Secret (`<cluster>-ca`, or `spec.certificates.serverCASecret`) and takes only `ca.crt`; the rest of that Secret, which holds the CA's private key, is dropped unread. When it can't be read the connection is encrypted without being verified, and says so.

## TLS

CloudNativePG enables TLS by default (`ssl = 'on'`, operator-managed server certificate) and its generated `pg_hba.conf` ends with `host all all all scram-sha-256` (`md5` on PostgreSQL 13 and older), so both TLS and plain logins are admitted for ordinary users; `hostssl … cert` rules cover only `streaming_replica` and the pooler. The server certificate covers the `<cluster>-rw`, `-r` and `-ro` Services (also with `.<namespace>` and `.<namespace>.svc`) ([postgresql_conf](https://cloudnative-pg.io/docs/current/postgresql_conf), [certificates](https://cloudnative-pg.io/docs/current/certificates)).

The session behaves like `sslmode=prefer` with rustls (`tokio-postgres-rustls`, `ring`; no OpenSSL): it tries TLS and falls back to plain **only when the server doesn't offer it**; a server that offers TLS and fails the handshake or the certificate check is an error (*The server's certificate was not accepted*), never a downgrade. Through a port forward the address is loopback, so the name checked is the Service's: `<cluster>-ro.<namespace>.svc` for a replica, `-rw` for the primary (`hostaddr` is the forward, `host` the name). The strip says which happened: *Encrypted, certificate verified* (checked against `ca.crt`), *encrypted, certificate not verified* (no CA could be read), or *not encrypted* (the server offered no TLS), found by asking the server (`pg_stat_ssl`).

## Read-only, enforced by the session

`freshkube_db::postgres::Postgres::open` sends `SET default_transaction_read_only = on`, `SET standard_conforming_strings = on` (the string literals we build rely on it) and our timeouts, then asks the server what it holds; a server that does not report `on` is refused, never used. Every request then runs as `ROLLBACK` (ends a transaction a cut-off request left open), `BEGIN READ ONLY`, a **server-side single-statement check**, the statement, `ROLLBACK` (also after a failure). The check prepares the text with the extended protocol, which the server refuses unless it is exactly one statement, so a splitter bypass can't reach `simple_query`. A request that is `SET`, `RESET`, `BEGIN`, `COMMIT`, `ROLLBACK` or more than one statement is also refused before it is sent (`readonly.rs`; a `$` after an identifier character belongs to the identifier, not to a dollar quote); that check only explains, the session is what enforces. Our own timeouts go out at connect, since DBFlux's drivers set none: `statement_timeout` (30 s), `lock_timeout` (5 s), `idle_in_transaction_session_timeout` (60 s), and a 10 s connect timeout. A table page asks for the cap plus one row to know there were more; at most 200 are shown, marked *Capped*. The schema and table listings are bounded too (500 schemas, 2,000 tables per schema, marked capped).

## The tab

The strip shows *Read-only session*, what protects the connection, who the session is (user and Secret kind, never a password), the pod and local port, the table summary, *Capped* when it is, Read again, and the writes gate: a disabled **Edit data** labelled *later slice*, with nothing behind it.

The browser sits beside the rows from 900 dp of page width and above them below it; the failure states scroll. The schema browser is the shared table: each schema is a group row, opened or closed by a click on it (its detail says "closed" or counts its tables); the first (`public`, else the first) opens on its own and the others read their tables only when opened. Rows carry the kind, the planner's row estimate (`–` before the table is analysed) and the total size. Choosing a table reads its columns and its first rows; a row opens its record in the Inspector (column, type, key and nullability, value; `NULL` as such).

## The Query tab

**Query** in the explorer's strip opens a dock tab for that database, one per database, beside the logs and shells. It uses the explorer's session (`QueryRequest::live`): no second forward and no second Secret read. If the explorer is closed or not connected the tab says *Connection closed*, keeps its editor and history, and runs nothing; Query again from the explorer once it is connected. The tab is saved nowhere and its Maximize is the dock's.

The strip says *Read-only session*, how the connection is protected, who the session is and the pod, and carries the **protection level of the tab's cluster** (the dock's `Origin::level`, followed live, held to Read-only when it is gone or unknown). Writes are E7 and are not here.

**What a run covers.** The selection, if it holds anything; else the statement at the cursor (`freshkube_db::statements`: statements end at a `;` outside quotes, identifiers, dollar quotes and comments, and a piece that is only comments is no statement; the cursor just after a `;` still belongs to its statement). A selection of several statements runs them in turn, each in its own read-only request, one result tab per statement, and stops at the first that fails, is refused or is cancelled; the rest read *Not run*. A run takes at most 50 statements; one more tab, *+N more*, says how many were left out. Command-Enter runs, Command-Shift-Enter shows the plan, Escape cancels while a statement runs.

**Read-only is still the session's.** Each statement is `BEGIN READ ONLY`, the server's single-statement check, the statement, `ROLLBACK`, then `SELECT pg_advisory_unlock_all()`, as in E1 with the unlock added: every ROLLBACK, the one that starts a request included, is followed by it. A statement that would write is sent and refused by the database (SQLSTATE 25006) and shown as *Refused: this session is read-only*, with a note that nothing was changed and it was not tried again; it is never retried, and no `COMMIT` is ever sent. `SET`, `RESET`, `BEGIN`, `COMMIT` and several statements in one request are *Not sent*, with the words that explain it.

**A guard, not a sandbox.** Until E4's reader role arrives, every live session is the application's own user, and a read-only transaction still lets some statements act on the server or other sessions. Freshkube refuses these before sending, each with words that say why: the first words `REINDEX`, `CLUSTER`, `VACUUM`, `ANALYZE`, `ANALYSE` and `CHECKPOINT` (exclusive locks and maintenance), `DO` (a block can build and run other statements) and `COPY` (`TO '/file'` and `TO PROGRAM` pass a read-only transaction), `EXPLAIN` with `ANALYZE` in any spelling and across any whitespace (it runs the statement), a `U&"…"` Unicode-escaped identifier outside string literals (it can spell a refused function's name), and these functions, matched by name as whole words in any case anywhere in the statement, a `DO` block's dollar quote and a schema-qualified or quoted name included: `pg_terminate_backend`, `pg_cancel_backend`, `pg_reload_conf`, `pg_rotate_logfile`, `pg_notify`, `set_config`, the `pg_advisory_lock`, `pg_advisory_xact_lock` family with their `_shared` and `try` forms, anything starting `dblink`, `lo_import` and `lo_export`, and `query_to_xml`, `query_to_xmlschema`, `query_to_xml_and_xmlschema` and `ts_stat`, which run a statement given as text. The list is by name, so it is not complete: a function it does not name still runs, inside a read-only transaction. The strip says *Application user* when the login is the application's own, because only the transaction then keeps it from writing; a reader role is the real fix. Guarantee 20 of the [safety suite](../SAFETY.md) holds these.

**Caps.** A statement that returns rows (`SELECT`, `WITH`, `VALUES`, `TABLE`) is read through a `NO SCROLL` cursor and fetches the row cap plus one (200 + 1), so a large result never reaches memory; the strip says *first 200 rows (row cap)*. `SHOW` and `EXPLAIN` are small and are cut at the cap. The statement, lock and connect timeouts are E1's, and a statement the server has not answered 40 s in is cancelled from here too.

**Cancel** stops the running statement on the server: `tokio-postgres`'s cancel request, a second short connection to the same forward with the session's TLS plan. It carries only the backend's process id and key, never a login or a password, so Cancel reads no Secret (a test against a recording socket proves what the cancel connection sends). Cancel does not take the session's lock, which the running statement holds. A cancel that arrives while the statement still waits behind an explorer read keeps it from starting. Closing the tab cancels what runs. A cancel and a timeout share one SQLSTATE and the server words them in its own language, so the tab decides: once Cancel was pressed, a time-limit answer reads *Cancelled*, and the server's English message is only a second signal. A Cancel that lands between the statement taking the session and starting is not lost: the cancel handle is filled before the flag is read, and Cancel sets the flag before it reads the handle.

**The plan** is `EXPLAIN (FORMAT TEXT)` on the first statement of the run, never `ANALYZE`, which would execute it. A statement that already starts with `EXPLAIN` is not sent as a plan (*Already a plan; use Run*); Run sends a plain `EXPLAIN` and refuses `EXPLAIN ANALYZE`. It opens as a result tab of its own, its lines drawn only while in view.

**History** lists what ran, newest first, at most 100 (text, local time, outcome), and clicking an entry puts it in the editor. It lives in memory for the tab's life: not saved, not in the audit log, a deep link or Search, and the login Secret is not in it. Closing the tab drops it; Clear empties it.

## Lifetime

The connection is user-started and belongs to its tab ([STATE_LIFETIMES.md](../STATE_LIFETIMES.md#database-explorer)). Reads (pick, connect, schemas, tables, columns, rows) are `Loader`s: a Tokio job plus a delivery task, dropped when the tab hides or connects again, landing only for the epoch they were asked in. A hidden tab reads nothing; showing it resumes what was cut short. The connected session is kept while hidden.

## Example data

`--fixture` uses `freshkube_db::fake` and no forward or Secret. `FRESHKUBE_DB_EXPLORE` (AGENTS.md) opens the first PostgreSQL database in the explorer and shapes how the connection ends; `query-app-user` does the same with the application's own login, so the *Application user* mark shows; `query` also opens the Query tab with three example statements run: the rows of `orders` (capped), an `update` the session refuses, and a statement that did not run after it. In the example, `pg_sleep` never answers until Cancel, and any write is refused. The example `shop` database has the schemas `public` and `audit`; `orders` has 250 rows (more than the cap), `customers` 12, `products` none.

## Dependency

`freshkube-db` depends on DBFlux's `dbflux_core` ([0xErwin1/dbflux](https://github.com/0xErwin1/dbflux), MIT OR Apache-2.0), pinned by `rev`, for `Value` and `DbError`. DBFlux's Postgres driver is not used: it needs a system OpenSSL through `native-tls` and `dbflux_ssh`, with no feature to drop them, and Freshkube ships none. `dbflux_core`'s Linux keyring needs libdbus, which `freshkube-db` builds from source (`libdbus-sys` with `vendored`), so nothing is installed on the build machine. The session is therefore ours, on `tokio-postgres`. `dbflux_core` brings `keyring` 3 (not optional), the dbus crates and `tree-sitter`/`zstd-sys` for two types; on a clean Linux debug build of `freshkube-db` that is about 190 CPU-seconds of the crate's roughly 575 (`zstd-sys` 64 s, `dbflux_core` 33 s, `dbus` and `libdbus-sys` 34 s); roughly a minute of wall-clock time on a multi-core runner. E2 may define `Value` and `DbError` locally until it needs the `Connection` trait. See the NOTICE file.
