# Applications, the Changes list and the change page

The behaviour of the Applications rail area, moved from [AGENTS.md](../../AGENTS.md) unchanged apart from its link paths and one stale name fixed (`Change::missing` is the field `Change.missing`). The paragraphs below are the three that AGENTS.md held, starting "Applications (`applications/`…", "The Changes list…" and "The change page…".

Code:

- `crates/freshkube-applications/src/` is the presentation (the `freshkube-applications` crate, which desktop reaches as `crate::applications`): the list, column, display, claims links, the application page (`page/`), the Changes list (`changes/`) and the change page (`change/`).
- `crates/freshkube-delivery/src/` is the cluster logic with no UI types: `applications/` (derive, `across`, `claims`, `read`, example data), `changes/`, `change/` (`live`, `example`), `entry/` (the source entries' clients and `pool`), `join/`, `kargo.rs`, `argocd.rs`, `source.rs`, `address.rs`.

Tests that prove it (the files with a `#[test]`, `#[tokio::test]` or `#[gpui_kit::test]`, found with `git grep -l '#\[test\]\|#\[tokio::test\]\|#\[gpui_kit::test\]'`):

- Desktop, `crates/freshkube-desktop/src/desktop/applications_tests/`: `mod.rs`, `page.rs`, `changes.rs`, `change.rs`, `setup.rs` (setup warnings, reload/save recovery, and unrelated Settings notifications), which drive the pages through the shell. The crate, `crates/freshkube-applications/src/`: inline tests in `across.rs`, `column.rs`, `display.rs`, `example.rs`, `links.rs`, `change/read.rs`, `changes/display.rs`; `change/tests.rs` covers the Chain's selection, both-axis reveal after layout, List order for every example change, keyboard-only cursor ring and link-pill clearance. "Switch and open" (`Pilot::open_on_entry`) is proved in `crates/freshkube-desktop/src/desktop/link_tests.rs`.
- Delivery, `crates/freshkube-delivery/src/`: `tests.rs`, `applications/tests.rs`, `applications/across/tests.rs`, `applications/claims/tests.rs`, `changes/tests.rs`, `change/live/tests.rs`, `change/live/across_tests.rs` (the change read across the workspace, each part from its entry), `entry/tests.rs`, `deployment_tests.rs`, `warehouse_tests.rs`, `provenance.rs`; inline tests in `address.rs`, `argocd.rs`, `digest.rs`, `github.rs`, `kargo.rs`, `observation.rs`, `read.rs`, `shared.rs`, `source.rs`, `entry/pool.rs`, `applications/example.rs`, `change/example.rs`.

Applications (`applications/`, [#521](https://github.com/skel84/freshkube/issues/521)) is its own rail area. It lists what delivery's `applications::derive` finds from Kargo Projects, Argo CD ApplicationSets and Applications, and the `app.kubernetes.io/part-of` label, grouped by the rule that found each one, with the selection in the Inspector. Its column (`applications/column.rs`, drawn in `desktop/shell/source.rs`) leads with Changes (below), then lists the same applications: All applications with its count, then each application under the rule that found it, in the table's order, at most 30, with a menu naming every one (what each is beside a name two share). A rule with nothing found has no section. A row opens the application's page and takes the fill, clearing a filter or chip that hides it. Without rows a note says why: Not connected, Reading… (also while a retry is in flight), Not permitted, No applications found, or Couldn't read with Retry. The page derives the column with each read and bumps a revision when it, or the application shown, changes; the column draws again only then, and only while it shows, never for the page's hovers or selections. The shell owns the page and tells it when it shows: it reads only while shown, when it has nothing or its last answer is 30 s old, and on Refresh; hiding drops the read in flight, whose late answer never lands, and another connection drops what was read. A live read takes each part from its source entry (delivery's `applications::across`, through `delivery::entry`'s clients, each dropped when the read ends): Kargo from `Sources::kargo`, Argo CD and its own cluster's labelled workloads from `Sources::argocd`, and each destination entry's labelled workloads, in one queue of at most four at a time, Kargo's and Argo CD's entries first. Kargo's and Argo CD's entries have the read's 45 s, and a destination's entry 30 s, connecting included; one that didn't connect by then is unreachable in its own name, one that connected but didn't finish says it didn't finish reading in time, and neither holds up the rest. Kargo is discovered once per read and its projects read four at a time. A part whose source is the open entry reads the open connection through `entry::reader`, with the other entries' deadlines; the workspace of one reads it through delivery's GET-only `ReadOnlyClient` under the page's deadline, as before. The page hands the read the entry the connection is with the connection (`set_source`), and the read is that pair's. The same applications show whichever entry is open, each part keeping its entry as its cluster, and an entry that isn't in the workspace or can't be reached is named in the banner and the empty states ("Couldn't reach ⟨entry⟩: …"), never none found; with nothing found, the state names one kind of failure and the banner every other. An Application whose destination the workspace maps to an entry whose labelled workloads weren't read is marked may be incomplete, naming that entry. A labelled workload on another entry is matched to the Argo CD Application whose destination maps to its entry and whose inventory lists it; one no such Application lists keeps "may be managed by an Argo CD Application", since one deploying there under an unmapped destination still may. With no destination mapped, the legend says labelled workloads were read on Argo CD's entry only. Argo CD is read where it runs: the namespaces of the workloads labelled `app.kubernetes.io/part-of=argocd`, at most three by name with the rest named as skipped, else its default `argocd` (`read::argo_namespaces`). Its applications are marked Scoped, with the namespaces read and how they were found in the mark, the legend and the empty state, never read in full; a Kargo application in a cluster whose Argo CD Applications aren't all read is at least Scoped, since its Stages promote to them. With nothing marking Argo CD and `argocd` holding no Applications, the banner says "Argo CD's namespace wasn't found; Applications elsewhere aren't listed", never none. The header's chips show their words beside the count on a page 960 dp wide or more (a 1280-point window beside the column), and always in the tooltip and label; the Inspector says a note shared by several parts once, with their names. The scope is the banner's and the mark's, never a row's note: the Inspector's tag shows the mark's short words with the sentence in its tooltip, and an Argo CD field says it once. The display is derived when a read arrives (`display.rs`): an application whose rule wasn't read in full in a cluster it spans is marked may be incomplete; a refused, failed or capped source beside found applications is a "May be missing" banner; with nothing found, refused and failed are their own states, and only when every source answered or isn't served is it "No applications found in what was read". Example data is delivery's acme workspace, invented clusters with Argo CD in `core-fra` and Kargo in `cicd-fra`. Enter, a double-click or the row menu's Open shows an application's own page (`applications/page/`) in the list's place, which a right-click selects without opening the Inspector; its breadcrumb, or Escape with no part selected, comes back with the list's selection kept. It reads nothing: the list hands it each read, and a read without its application closes it. Its rows are the parts grouped by kind, with `claims` (`applications/claims/`) as the Link column: Confirmed when both sides were read and agree (a Project's Stage, an ApplicationSet's Application, a workload whose tracking annotation or instance label names the Argo CD Application whose inventory lists it), By label when only its `part-of` label says so, Claimed when only an annotation, name, override or an Argo CD inventory that the workload doesn't name back does, Unknown when a side couldn't be read. A workload is never surer than the Application it came through: one tracked by an Application that only names a Kargo Project is Claimed on that Project's page, and says why. A labelled part in a cluster whose Argo CD Applications weren't all read keeps its label's link, and its Read from says what wasn't checked and where ("Argo CD read in ⟨namespace⟩ only on ⟨cluster⟩", "Argo CD not read on ⟨cluster⟩"). The page's breadcrumb and the Inspector name what the application is (Kargo Project, Argo CD Application or ApplicationSet) beside its name, since two may share one. A Kargo application's page has a "May be missing" row for the Argo CD Applications its Stages promote to wherever Argo CD wasn't read in full. The legend draws each word with its glyph, Confirmed in normal ink and Unknown dim. A read that may have left parts out is a "May be missing on ⟨cluster⟩" group row with the Unknown ring, never an empty group; the Inspector's Link section shows each side, why, and any lower rule's claim. O, the row menu's Open in Resources (a right-click selects without opening the Inspector) and the Inspector's button open the selected part in Resources on its Overview (`applications/links.rs`): the list passes its `ResourceLink` to the shell, which opens it through `Pilot::open_object` like every cluster-qualified link, so a part in a cluster that isn't open gets that path's notice and nothing moves. The button and the menu item are greyed out for such a part, with why in the tooltip; O sends it anyway. A part whose cluster is another entry of `workspace.json`, by name, offers Switch and open instead (the whole sentence in its tooltip, "Switch to ⟨cluster⟩ and open" in the menu): the page emits `SwitchLink`, and `Pilot::open_on_entry` (`desktop/switch.rs`) asks "Switch to ⟨cluster⟩ to open ⟨Kind⟩ ⟨name⟩?" through `shell::asking`, which folds running shells into the one question ("… and end the shell in ⟨pod⟩?") and never names forwards, since they keep running. Cancel changes nothing; Switch activates the entry as the cluster list does and holds the link, by name, until that entry's connection answers, then opens it on that connection; another link, another switch or a failed one drops it. An entry the workspace no longer lists is refused with the notice. The shell tells the page the workspace's entries and the open one (`ApplicationsPage::set_clusters`); in example data the acme cluster the open entry is, else `core-fra`, stands for the open example cluster, and `dev-fra`, `prod-ams` and `prod-lon` hold labelled Deployments (delivery's `applications::example::environment_objects`), each but loyalty's listed by its stage's Application and naming it back. Each read carries which connection each cluster is: a live read's cluster is its entry's, the open one's its connection; example data maps the acme cluster the open entry is, else `core-fra`, to the open example cluster, whose Resources list the Kargo Projects, Stages, Warehouses, Argo CD Applications, ApplicationSet, the `status/status-page` Deployment and Argo CD's own Deployments, labelled `part-of=argocd` so the example finds it in `argocd` as a live read would, from delivery's `applications::example::core_objects` (`resources/example/acme.rs`, with UIDs clear of `WORKLOADS`), and leaves the other acme clusters unmapped, so their parts open only after a switch, or are refused when no workspace entry is theirs.

The Changes list (`applications/changes/`, `delivery::changes`) leads the Applications column, above All applications, and shows in the list's place: a table page with one row per Kargo Freight, its pull request (from its build's Pipelines as Code annotations, else its commit), title with its application after it, dimmer and cut first, and age, then one Stages cell: the row's own project's Stages in promotion order, each a glyph (Confirmed, Claimed, Unknown or Refused) or – (the Stage runs other Freight) beside its name, the Stages it has no room for counted in a muted +N at its end with the whole list in its tooltip, from the change page's own join; the row's glyph is its weakest Stage. Groups: Not fully confirmed, then Confirmed to the running pods and Not running in any Stage, newest first, the last two folded with their chevrons while anything needs a look. At most `MAX_FREIGHT` (50) Freight a project, the rest counted, with refused and unread projects, in a May be missing banner; with no rows, refused and failed are their own states. The Inspector shows the selection's Stages with why and its trail, and Enter, a double-click, the row menu's Open or Open change shows the change page in its place, with Changes as the breadcrumb. It reads only while shown, as the change page does: hiding drops the read, showing it again reads once 30 s old, and Refresh reads again; a remap or a new Argo CD namespace (where the Applications read found it, on the entry asked for Argo CD; reset with the connection) reads a live list again. A live read (delivery's `changes::live`) reads each part from its source entry through the change page's pool (below), Kargo's entry unreached failing the list in its name; the pool asks each entry through its own shared reader, so what its changes share (each project's Kargo kinds, Argo CD's Applications, the ConfigMaps, a namespace's workloads, discovery) is asked once an entry, through `entry::reader`, whose requests have 5 s each and a listing 5 s for each of its pages. Projects take four turns in whatever order they answer, so one that hangs holds one turn, never the others, and each project's changes are followed as soon as it answers, four at a time across the read; what hasn't answered within `BUDGET` (90 s) is left out with why while the rest shows, and changes not followed in time are counted in the banner. The column leaves room under Changes for the workspace's delivery sources.

The change page (`applications/change/`, `delivery::change`) follows one change from its pull request to the pods that run it, as a trail page ([DESIGN.md](../DESIGN.md#the-change-page)). On a Kargo application's page, F, the row menu's Follow or the Inspector's button on a Stage whose change was read shows it in the application page's place, on that Stage's gates; its breadcrumb, Escape with nothing selected, or a click on the application's filled row in the column comes back, and opening another application drops it. The list's read carries where changes come from (`Changes`): example data's, delivery's invented `checkout` Freight `wonky-otter`, or a live read's, each Stage's current Freight. The page reads the change itself while it shows (`change/read.rs`): live through `delivery::change::live`, which GETs the Freight, then collects and joins across the workspace, with every link's confidence the join's. Each part is read from its source entry (`workspace::Sources`) through one `delivery::entry::pool::Pool` per read: Kargo's Freight, Stages, Warehouses and Promotions from Kargo's, the builds from theirs, Argo CD's Applications and `argocd-cm` from Argo CD's, the open entry through the open connection and every other through a client made for the read alone, connected once, at most four connecting at a time (connected entries read at once), and dropped with the read; the first round, the Freight's GET included, has the rest of the 45 s budget, and each destination 30 s from when it is asked for, its wait to connect included, never past the read's end. The workspace of one reads the open connection through delivery's GET-only `ReadOnlyClient` under the page's 60 s, as before; the Changes list reads it through `entry::reader`. A Stage's destination is a cluster only when its Application was read and its destination is Argo CD's own cluster or one the workspace's `destinations` map (delivery's `change::live::Mapping`): its workloads, ReplicaSets and pods are read on that entry and joined as on one cluster, so they can be Confirmed. A destination entry that was asked for and couldn't be read names itself and makes its Stage Unknown, naming the entry; the workloads Argo CD's `status.resources` reports there stay Claimed rows on that entry, saying only Argo CD's status says so. A destination no read asked for keeps them Claimed. A part whose entry is missing, unreachable, refused or not served is named on its hop and in the page's May be missing banner (`Change.missing`, which the Changes list folds into its own), never as none found; Kargo's entry unreached fails the change in its name. Otherwise it is Unknown with why (Applications not read in that namespace, no Application found, not running the Freight, a destination not mapped, mapped to an entry the workspace no longer lists, or to more than one), and the Inspector names a live cluster by its context, never its connection key, as do the links' reasons (`Evidence::name`). Hiding drops the read in flight, showing it again reads once what it has is 30 s old, Refresh reads again, and a failed refresh keeps the last answer marked stale. Its rows are hops in travel order, grouped Build, Freight, then each Stage; a Stage whose every row is fine folds while anything else needs a look, except one whose entry wasn't read. A Stage's group row adds its reach, as the Changes list's cell has it, when that is less than Confirmed ("pods on ⟨cluster⟩ unknown", "… claimed", "⟨kinds⟩ refused"), with the weaker of its rows' glyph and that, and then never folds itself. Detail cuts at a word with its whole text in the tooltip (`freshkube_ui::table::word_cell`, #522). O, the row menu and the Inspector's buttons open objects in Resources through `Pilot::open_object`, greyed out with why for a cluster that isn't open; an object on another workspace entry offers Switch and open instead ("Switch to ⟨entry⟩ and open" in the menu), which emits `ChangeEvent::Switch` and goes through `Pilot::open_on_entry`, as on the application page. The shell hands the page the workspace's entries and its `Mapping::of` (`Clusters`); a live read resolves Stages through it, with its hint to map an unmatched one in Settings › Workspace on, and a change to either reaches a change page already open at once: its links follow, and a live one reads again while shown, else when it next shows. The tools' pages open in the browser only at an http or https address the cluster records (delivery's `Address`, which drops user info, query and fragment): Argo CD's from `argocd-cm`'s `url`, Kargo's from `kargo-api`'s `ADMIN_ACCOUNT_TOKEN_ISSUER` in `kargo`, both ConfigMap GETs with their own 5 s deadline, never a Secret; a run's pull request, commit and run page from its Pipelines as Code annotations (a commit on the repository's host only; a run page keeps a `#/…` route, as the Tekton Dashboard's, and Pipelines as Code's fallback console is none). Without one a button is greyed out with why. The header's Open in Kargo ↗ and Copy link open and copy the Freight's Kargo page, and Copy link says Copied. A run's Logs open its failed task's pod, else the one that ended last, in the dock as a pod's logs on the open connection, with every step; greyed out for a cluster that isn't open. A Deployment's Compare in Observability opens Coroot's revision of it by its current ReplicaSet's pod-template hash (`ObservabilityPage::open_revision`, [COROOT.md](../COROOT.md#from-the-change-page)), greyed out with why for a cluster that isn't open, a Deployment whose pods aren't confirmed to run the Freight, or an Argo Rollout. It never approves, promotes or syncs.

Stage naming (`delivery::argocd::StageNaming`, setup key `delivery.stage_naming`, [SETUP_FILE.md](../SETUP_FILE.md), [#804](https://github.com/skel84/freshkube/issues/804)) ties an Application with no authorized-stage annotation to its Kargo Stage by a name template. With a `project_key` it is a claim by convention (`StageClaim::NamedByConvention`); without one the name alone claims (`StageClaim::NamedOnly`, "matched by the configured name template only"), weaker still. Both are Claimed on the Link column and the change page, never Confirmed: the join caps a name-only link at Claimed even when a Promotion's pushed commit is the synced revision (`join/argo.rs`, "found by the naming template only"). The annotation still wins, and an annotation naming another Stage blocks the name. When more than one Application claims a Stage by name only, `Evidence::claims_stage` takes the claim from all of them, so the change page and the Changes list link none and each says "N Applications match the naming template for this Stage". On the Applications page a name that fits Stages of more than one project (`Application::name_only_fits`, with each Stage counted once however many sessions read it) puts the Application in none of those projects and keeps it with Argo CD under a note saying which Stages it fits; a name-only member of a Project shows "Naming template" as its basis (`Basis::NamedByTemplate`). The page takes the key from the setup (`ApplicationsPage::set_setup`) and hands it to the list's derivation, the Changes list and the change page; a reload that changes it reads the list again, and the change reads again with it.

Builds by image digest (`delivery::tekton::read_builds_by_digest`, `results::supplement_digests`, `join::build::digest_links`; tests in `digest_builds_tests.rs` and `results/tests/digest.rs`): a Freight that names an image and no commit (neither a commit nor an `org.opencontainers.image.revision`) is joined to its build by an `IMAGE_DIGEST` result of a PipelineRun or one of its TaskRuns (alone or with an `IMAGE_URL`, and the prefixed pairs, as Chains' type hints have them), in the namespace `delivery.build_namespace` names ([SETUP_FILE.md](../SETUP_FILE.md)), read from the cluster the commit reads use; without the key nothing is listed and the Build hop says so, naming the key. A result can't be selected on, so the read lists the namespace's PipelineRuns and TaskRuns (the reader's page cap each, 5 pages of 200; never by selector, never across namespaces) and compares in memory; a run found only by a TaskRun result outside the listing is read by name, at most `MOST_TASK_READS` (10) times. A capped listing that finds nothing says the build may be among those not read. The archive is searched in the first ten PipelineRun records it returns for the namespace only (`Client::first_pipeline_runs`, no order asked for, one TaskRun listing each; unchecked against a live Results server), and only after a live read that wasn't capped or failed, as for a commit. The link is Image → PipelineRun on `Key::Digest`, Confirmed because a result reports the digest, and the PipelineRun → Freight link joins on the same digest; no Commit → PipelineRun link is made, since no commit is known. When the change names a commit too, the digest wins as the join key: a run found by both keys is the commit's, and the digest join is Claimed, with its reason and the conflicting builds, when a build of the commit reports another digest for the Freight's image or the build the digest found reports another commit. A digest is content-addressed, so the build's `IMAGE_URL` is not compared with the Freight's repository: a mirror or a retag of the same digest is the same image and stays Confirmed. With the key set, a Freight that names a commit is searched by digest too. Example data: `FRESHKUBE_APPLICATIONS=image-only`.

The setup owner hands Applications the last good setup and its current problem together through `desktop/startup/setup.rs` and `Pages::set_setup`, once per `SetupFile.read_revision`. A refused file at launch reaches the pages even with no accepted setup. The Changes list and change page keep the sanitized `SetupFile::problem_words` text in their source-warning area: “freshkube.yaml isn't used: ⟨why⟩. …”, with “The last good setup stays in use.” when there is one, else “Freshkube starts as with no file.” They never show YAML bytes or key or token values. An already-open change updates too, and a change opened later inherits the warning from either the Changes list or an application's Stage. A changed problem advances the revision even when the accepted setup is unchanged; accepting the file again by reload or save clears the warning. Unrelated Settings notifications repeat no hand-off and do not replace or flash the banner. This is [#802](https://github.com/skel84/freshkube/issues/802)'s 0.17.0 banner slice; per-item recovery and the in-cluster alias remain for 0.17.1.

The change page's Chain view (`change/chain.rs`, `change/trail.rs`) shares List's selection and Inspector. Within each column it keeps List order, including Stage promotion order, while the service map retains its crossing reduction. The canvas tracks both scroll axes and reveals a selected card until the layout settles, including when the Inspector stacks at narrow widths or larger text sizes. Mouse selection keeps the ordinary accent border; keyboard navigation and Tab entry add the thick cursor ring (on the first card without selecting it when there is no selection), cleared by a click or blur. Link pills sit level with their targets, clear of neighbouring curves ([DESIGN.md](../DESIGN.md#the-chain-view)).

Both delivery reads (the Changes list and an opened change, from either the list or an application's Stage) receive the setup's workspace-wide `supply_chain.public_key_file`, `evidence`, `transparency_log` and optional `transparency_url`. The log is off by default and off reads no log or Chains configuration. When on, a verified signature needs a matching log entry to confirm the supply-chain link; the log address is the setup's HTTPS URL, else the builds entry's `chains-config` `transparency.url`, never an annotation's host or a public default. No token or Results CA reaches the log. A setup reload, including an identical explicit Reload, advances each read owner's setup revision, cancels old work and rejects old completions; a changed switch or URL takes effect on the next read while shown. Unrelated Settings notifications keep current reads.

The hand-off and reload regressions are in `crates/freshkube-applications/src/wire_tests/mod.rs`; delivery's `change/live/tests.rs` and `changes/tests.rs` check the settings through to the Plan. Delivery's `rekor/tests.rs` exercises the fake HTTPS log and token isolation with an authenticated Results read, using the existing delivery-only client helper. These tests use invented data and no application test transport injection.
