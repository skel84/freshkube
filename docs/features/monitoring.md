# Monitoring

The behaviour of the Monitoring rail area and the CPU and memory history charts, moved from [AGENTS.md](../../AGENTS.md) unchanged apart from its link path: the paragraph starting "Monitoring (`freshkube-monitoring`'s `page/`…". The design, the panels as built and the live checks are in [docs/MONITORING.md](../MONITORING.md).

Code:

- `crates/freshkube-monitoring/src/page/` is the page: `mod.rs` (`MonitoringPage`), `board.rs`, `catalog.rs`, `connection.rs`, `source.rs`, `layout.rs`, `markers.rs`, `settings.rs` and `view.rs`.
- `crates/freshkube-monitoring/src/history/` is the history chart a pod's Overview and the node pane show; `derive/` and `panel/` turn a frame into the Console panels; `store.rs` is `monitoring.json`; `lib.rs` holds the private `dispatch` both readers use.
- `crates/freshkube-core/src/monitoring/` holds discovery, the built-in dashboards, the catalog, the history and marker reads, the transport and the example data.
- `crates/freshkube-monitoring/src/alerts/` is the Alerts, Rules and Silences pages (`mod.rs` `AlertsPage`, `display.rs`, `table.rs`, `view.rs`); `crates/freshkube-core/src/monitoring/alerts/` reads Alertmanager, vmalert and PrometheusRule objects (`model.rs`, `parse.rs`, `discover.rs`, `read.rs`, `rules.rs`, `state.rs`, `drive.rs`, `example.rs`); `crates/freshkube-desktop/src/desktop/alerts/` is the session alert read.

Monitoring (`freshkube-monitoring`'s `page/`, [docs/MONITORING.md](../MONITORING.md)) is its own rail area; its column lists the built-in dashboards and the user's folder of Grafana JSON (Settings → Dashboards folder, saved in `monitoring.json` beside the preferences). The shell owns the page and tells it when it shows; a hidden page finds nothing, resolves nothing and asks no panel. Showing it finds Prometheus for the context (the remembered Service first), resolves the variables, then asks only the panels in or near the viewport. Every change that asks again takes a new generation, and an older answer is dropped; hiding drops every request and the auto-refresh timer. Another source rebuilds the dashboard, so one cluster's answers never show as another's. Panels draw only Console colours. Timeseries also draw deploy and node markers (`monitoring/page/markers.rs`), read per generation from ReplicaSet metadata, Nodes' Ready condition, Node events and, with Talos, boot times; the page filters them by its toggles and the namespace and node variables before handing them to the panels. A pod's Overview and the node pane show CPU and memory over the last hour (`monitoring/history/`) from the Prometheus the page confirmed or remembers for the context (`MonitoringPage::history`, pushed on `MonitoringEvent::History`); without one they show and read nothing. A pod's chart reads while its drawer shows Details, at any scroll, and the node pane's while its Overview shows.

**The setup file's metrics scope** (`docs/SETUP_FILE.md`, "Metrics"). `freshkube_core::monitoring::scope::resolve` reads `metrics.mode`, the open entry's own `source` and the central store into one `Resolved`: `Discovery` (automatic, or a context that is no entry), `Own`, `Central` with its `Matcher`, or `Unknown` with the reason. The shell hands the last good setup to the page (`Pages::set_setup`, then `MonitoringPage::set_scope` from `desktop/entity_pages.rs`), with the cluster that hosts a central Service. A scoped page connects to that store and nothing else: no discovery, no source chosen in Settings, nothing remembered for the context. An entry the file gives no store (`Unknown`) shows "No metrics source" and the reason, with no Try again, since nothing was asked (`Connection::Unknown`); a failure reading a store that another entry's cluster hosts names that entry, "Couldn't reach the metrics store through cluster-b: …" (`through_host`), so it isn't read as the open entry's own cluster failing. A central store is read through a `Prometheus` carrying the entry's `Matcher`, which parses every `query` and `match[]` and adds `label="value"` to every selector (`monitoring/matcher.rs`); the history charts of a pod's Overview and the node pane take that same `Prometheus` through `MonitoringPage::history`. The panel's query view shows the scoped text that was sent. A new scope drops the connection, the board and every read in flight, and an answer for the previous scope never draws.

Tests: `page/tests/scope.rs`, `history/tests.rs` (`the_history_of_a_scoped_store_sends_the_entrys_matcher`), core's `monitoring/matcher.rs` and `monitoring/scope/tests.rs`, and `desktop/tests/metrics.rs`.

`PanelView::set_focused_marker` takes an optional start second. Matching markers in the panel's existing window draw heavier and keep their labels visible; clearing it restores ordinary markers. It changes neither the marker types nor the window. `panel/tests/` proves the drawing, labels, same-second matches and clearing.

## Alerts, Rules and Silences

Read-only (#884, slice 1). Alerts, Rules and Silences sit at the top of the Monitoring column, above the dashboards, and show in the dashboard's place (`MonitoringPage::show_alerts`, `Section`). They are table pages on the shared components: Alerts grouped by severity and then by alert name, with each row's state (firing, pending, silenced, inhibited), since when, its labels as chips and its summary; a filter, a toggle for silenced and inhibited alerts, and an Inspector with the runbook link (web addresses only) and every label, where a label that names an object (`pod`, `namespace`, `node`, the workloads) opens it. Rules are grouped by rule group, with each rule's health, last evaluation and last error, a failing rule as a problem; Silences are grouped active, pending and expired, with their matchers, creator, comment, end and the alerts each mutes now. Nothing here silences or expires.

**Where it looks** (`monitoring::alerts::Scope::of`, from the setup's metrics `Resolved`): with automatic discovery or an entry's own source, the open cluster's own Alertmanager and vmalert (`alertmanager-operated`, an `app.kubernetes.io/name` of `alertmanager` or `vmalert`, a name containing `alertmanager`, port `web`, `http` or 9093, and 8880 for vmalert), read through `services/proxy` with GET only. With a central store, the namespace of the store's Service on its hosting cluster, and only the alerts carrying the entry's cluster label: a store whose alerts carry none shows nothing (`Unknown::NoClusterLabel`), never every cluster's, and its vmalert rules aren't shown, since they aren't per cluster. A central store given as a URL names nowhere to look. PrometheusRule objects are listed as plain objects; with no vmalert evaluating them every rule's health is Unknown, never OK. Several Alertmanagers that answer are named, and replicas of one are deduplicated by fingerprint.

**What it never says.** Not found, can't read, unread, stale and refused are states of their own, and none reads as "no alerts": only a current read with nothing active is "All quiet", and it names what was read. A refresh that failed over an earlier read keeps its rows, marked as the last read.

**The alert read.** Beside the Kubernetes summary there is one session-owned read of the active alerts (`desktop/alerts/`, [STATE_LIFETIMES.md](../STATE_LIFETIMES.md#the-session-alert-read)). It feeds Overview's attention rows (critical and warning alerts, Failing and Warning; last-known evidence and an unreadable source as Unknown) and the rail's Monitoring mark and its Alerts row; Unknown has its own mark, never a problem's. The pages read only while shown.

**Example data** (`monitoring/alerts/example.rs`) answers `--fixture` in the shape `FRESHKUBE_ALERTS` names, and `FRESHKUBE_PAGE=alerts`, `rules` or `silences` opens a page.
